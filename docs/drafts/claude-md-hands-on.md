오늘 이 글 하나만 끝까지 읽으시면 위치 정하기부터 점검까지 직접 해 보실 수 있습니다.

## 🛠️ 시작하기 전에 - CLAUDE.md는 왜 필요할까요?

Claude Code 세션은 매번 새 컨텍스트로 시작합니다.
어제 나눈 대화를 오늘 기억하지 못하니, 매번 알려 줘야 하는 내용이 생기죠.
그 내용을 미리 적어 두는 파일이 바로 CLAUDE.md입니다.

비슷한 장치로 Claude가 스스로 메모하는 자동 메모리도 있습니다. 둘의 차이는 이렇습니다.

| 구분 | CLAUDE.md | 자동 메모리 |
| :--- | :--- | :--- |
| 작성자 | 내가 직접 | Claude |
| 내용 | 지침과 규칙 | 배운 점과 패턴 |
| 불러오는 때 | 매 세션 시작 | 매 세션 시작 |

* **준비물:** 터미널에서 `claude`를 실행할 수 있는 프로젝트 폴더
* **소요 시간:** 초안은 금방 나오고, 다듬는 일은 쓰면서 조금씩 이어집니다
* **난이도:** 입문
* **기준:** 이 글은 2026년 10월 27일에 확인한 공식 문서를 따릅니다. 기능마다 필요한 버전이 달라서, `claude --version`으로 본인 버전을 한번 확인해 보세요

> 📌 **전문가 Tip:** 같은 실수를 두 번째 바로잡고 있다면 그게 CLAUDE.md에 넣을 타이밍입니다. 처음부터 완벽하게 채우려 하지 말고, 반복되는 말부터 옮겨 적어 보세요.

## Step 1. 파일은 어디에 만들까요? - 위치 고르기와 /init 초안

처음 시작할 때 가장 많이 헷갈리는 부분이 파일 위치입니다.
범위에 따라 놓을 곳이 달라요.

| 범위 | 위치 | 누구에게 적용되나 |
| :--- | :--- | :--- |
| 프로젝트 | `./CLAUDE.md` 또는 `./.claude/CLAUDE.md` | 팀 (버전 관리에 포함) |
| 사용자 | `~/.claude/CLAUDE.md` | 나, 모든 프로젝트 |
| 로컬 | `./CLAUDE.local.md` | 나, 현재 프로젝트 |

[IMAGE: 비교표 | 설명: CLAUDE.md 위치를 범위별로 비교한 표. 프로젝트, 사용자, 로컬 3행에 각각 파일 경로와 적용 대상을 짧게 정리]

입문자라면 프로젝트 루트의 `CLAUDE.md` 하나로 시작하시면 됩니다.
다른 사람과 공유하고 싶지 않은 개인 취향은 `CLAUDE.local.md`에 적고 `.gitignore`에 추가해 두세요.

아래 순서대로 차근차근 따라와 주세요.

1. 프로젝트 폴더에서 `claude`를 실행합니다.
2. `/init`을 입력합니다. (코드베이스를 분석해 빌드 명령, 테스트 방법, 발견한 규칙이 담긴 초안을 만들어 줘요. 이미 CLAUDE.md가 있으면 덮어쓰지 않고 개선안을 제안합니다)
3. 만들어진 파일을 열어 봅니다. (`/memory`를 입력하면 메모리 파일 목록이 나오고, 거기서 편집기로 열 수 있어요)
4. 초안을 그대로 두지 말고 다음 단계에서 줄을 덜어 냅니다.

[IMAGE: 다이어그램 | 설명: CLAUDE.md 초안을 만드는 순서를 위에서 아래로 보여 주는 다이어그램. 1 claude 실행, 2 /init 입력, 3 초안 열기, 4 줄 덜어내기 네 칸을 화살표로 연결]

`/init`이 어렵게 느껴지시면 빈 파일에서 시작하셔도 괜찮습니다.
아래 틀에 빈칸만 채워 보세요. 공식 문서의 "명령 / 규칙 / 함정" 구성을 입문자용으로 풀어 본 예시입니다.

```markdown
# 프로젝트 한 줄 소개
- (무엇을 하는 프로젝트인지 한두 줄)

# 명령어
- 실행: (명령)
- 테스트 전체: (명령)
- 테스트 하나: (명령)

# 규칙
- (예: 응답 문구는 한국어로 쓴다)
- (예: 기능을 바꾸면 해당 문서도 함께 고친다)

# 주의할 점
- (Claude가 코드만 보고는 모르는 함정 한두 개)
```

## Step 2. 무엇을 적고 무엇을 지울까요? - 제 CLAUDE.md를 예로

기본이 끝났다면 이제 내용을 채울 차례입니다.
공식 문서의 원칙은 단순해요. Claude가 코드만 봐서는 알 수 없는 것만 적으라는 겁니다.

[IMAGE: 포인트카드 | 설명: CLAUDE.md 작성법에서 적어 둘 내용 4가지 카드. 확인 명령, 오해하기 쉬운 곳, 저장소 밖 결정, 두 번 교정한 것]

* **확인 명령:** 테스트, 린트, 파일 하나만 돌리는 법
* **오해하기 쉬운 곳:** 남아 있지만 새 코드엔 쓰면 안 되는 옛 패턴 같은 것
* **저장소 밖 결정:** 코드에 나오지 않는 팀의 약속이나 배포 방식
* **두 번 교정한 것:** 같은 말을 두 번 했다면 적어 둘 후보

반대로 줄이는 쪽도 정해져 있습니다.
아키텍처나 파일 구조 설명은 Claude가 저장소를 직접 읽으니 거기 없는 것만 남기라는 안내가 있어요.
문장은 검증할 수 있게 쓰는 편이 좋습니다.

| 이렇게 쓰면 | 이렇게는 피하세요 |
| :--- | :--- |
| 2칸 들여쓰기를 쓴다 | 코드를 잘 정리한다 |
| 커밋 전에 `npm test`를 실행한다 | 테스트를 열심히 돌린다 |

참고로 IMPORTANT 같은 강조어를 덧붙여도 해결되지 않는다고 합니다. 평이한 문장이면 충분하고, 강조가 쌓이면 오히려 규칙을 과하게 적용할 수 있다는 설명이에요.

### 제가 쓰는 파일은 이렇게 생겼어요

저는 제 저장소에 CLAUDE.md를 두고 쓰는데요.
6개 섹션, 67줄 정도로 공식 권장인 200줄 미만 안에 들어옵니다.
담은 내용은 다섯 가지입니다.

[IMAGE: 포인트카드 | 설명: 필자의 CLAUDE.md에 담긴 내용 5가지 카드. 실행·테스트 명령, 함정, 하지 말 것과 이유, 구조, 에이전트 파일 작성 규칙]

* 서버 실행과 테스트 명령
* 함정 (예: 설정에 `-q`가 이미 있어서 또 주면 요약 줄이 사라진다는 점)
* 하지 말 것과 그 이유
* 폴더와 계층 구조
* 에이전트 파일을 쓸 때의 규칙

가장 공들인 건 "하지 말 것 + 이유" 줄입니다.
`innerHTML`은 쓰지 않는다고 적고, 토큰이 `localStorage`에 있어서 XSS가 곧 토큰 탈취라는 이유를 붙였어요.
확인 창도 `confirm()` 대신 화면 안 `askConfirm`을 쓰라고 하고, iframe에서는 `confirm()`이 항상 false라는 이유를 함께 적었습니다.

이유까지 적어 두면 코드만 봐서는 알 수 없는 사정이 전해지고, 규칙을 어길 때 되돌리는 수고도 줄어들 거라고 생각했어요.

솔직히 다시 읽어 보니 고칠 곳도 보입니다.
구조를 설명한 줄에는 저장소를 읽으면 알 수 있는 내용이 섞여 있어서, 공식 기준으로는 줄일 후보예요.
한 줄이 지나치게 긴 곳도 있습니다.

> 📌 **전문가 Tip:** 여러분의 파일이 길어졌다면 `/doctor`가 코드에서 알 수 있는 내용을 덜어 내자고 제안해 줍니다. 함정이나 이유가 적힌 줄은 남기는 쪽이고요. 다만 `/doctor prompt-audit`은 v2.1.283 이상이 필요하니 버전을 먼저 확인하세요.

## Step 3. 잘 읽히고 있을까요? - 확인하고 낡지 않게 관리하기

파일을 만들었다고 끝이 아닙니다.
Claude가 실제로 읽고 있는지부터 봐야죠.

1. 세션에서 `/context`를 실행합니다.
2. **Memory files** 목록에 내 파일이 있는지 확인합니다. (목록에 없으면 Claude가 볼 수 없어요)
3. 하위 폴더의 CLAUDE.md는 시작할 때 로드되지 않아 목록에 안 보입니다. (그 폴더의 파일을 읽게 하면 터미널에 `Loaded` 줄이 나와요)

### 시간이 지나면 낡는다는 것

제가 겪은 일도 하나 말씀드릴게요.
서브에이전트 `image-maker`를 새로 만들었는데, CLAUDE.md의 에이전트 목록에 추가하는 걸 빠뜨렸습니다.
나중에야 알아채서 고쳤어요.

코드나 파일이 바뀌면 CLAUDE.md도 같이 고쳐야 낡지 않습니다.
없는 파일을 가리키는 줄이나 서로 모순되는 줄이 남으면, Claude도 헷갈릴 수 있으니까요.

### CLAUDE.md의 한계 - 꼭 지켜야 하는 규칙은 어디에 둘까요?

CLAUDE.md는 강제 장치가 아니라 맥락을 전하는 파일입니다.
Claude가 읽고 따르려 하지만, 엄격하게 지켜진다는 보장은 없다고 공식 문서도 말해요.
그래서 목적에 맞는 곳에 나눠 두는 게 좋습니다.

| 수단 | 맞는 용도 |
| :--- | :--- |
| CLAUDE.md | 항상 알아야 할 사실과 선호 |
| 경로 한정 규칙 (`.claude/rules/`) | 일부 파일에만 해당하는 규칙 |
| 스킬 | 여러 단계의 절차, 필요할 때만 읽기 |
| 훅 | 예외가 없어야 하는 규칙, 자동 실행 |

[IMAGE: 비교표 | 설명: CLAUDE.md와 함께 쓰는 수단 비교표. CLAUDE.md, 경로 한정 규칙, 스킬, 훅 4행에 맞는 용도를 한 줄씩 정리하고 CLAUDE.md 작성법의 한계를 보완하는 흐름을 보여 줌]

> 📌 **전문가 Tip:** "named export를 선호한다" 같은 취향은 CLAUDE.md에, ".env를 읽지 않는다"처럼 예외가 없어야 하는 규칙은 훅이나 거부 규칙에 두세요. 강제 장치를 너무 늘리는 것도 권하지 않는다고 합니다.

### 막힐 때 자주 묻는 질문

**Q. 적었는데 안 지켜져요.**
A. 순서대로 점검해 보세요. 로드 여부, 파일 위치, 지침의 구체성, 파일 간 상충, 그리고 Claude Code가 자체로 넣는 커밋·PR 지침과의 충돌입니다.

[IMAGE: 포인트카드 | 설명: 적어 둔 CLAUDE.md가 지켜지지 않을 때의 점검 순서 5단계 카드. 로드 확인, 위치 확인, 더 구체적으로, 상충 점검, 커밋·PR 지침 충돌 확인]

**Q. 얼마나 길게 써야 하나요?**
A. 공식 권장은 파일당 200줄 미만입니다. 길수록 컨텍스트를 더 쓰고 준수율이 떨어질 수 있다고 해요.

**Q. 다른 파일을 가져와 쓸 수 있나요?**
A. `@경로` 문법으로 가능합니다. 다만 정리에는 도움이 되어도, 가져온 파일이 함께 로드되니 컨텍스트 비용은 줄지 않아요.

**Q. 대화 중에 말한 건 유지되나요?**
A. 대화로만 준 지침은 `/compact` 뒤에 사라질 수 있습니다. 오래 가져가야 한다면 CLAUDE.md에 적어 두세요.

**Q. 저장소에 AGENTS.md만 있는데요?**
A. CLAUDE.md가 없고 AGENTS.md만 있으면 AGENTS.md를 읽습니다. 이 동작은 v2.1.277 이상에서 확인되는 내용이라 버전을 확인하세요.
