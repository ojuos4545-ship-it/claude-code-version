# 클로드 코드 권한 모드 사용법, 허락 묻는 기준 정하는 3단계

> 💡 **한 줄 요약:** 클로드 코드 권한 모드는 "Claude가 묻지 않고 해도 되는 일의 범위"를 정하는 스위치입니다. 조사일 기준 새 세션은 auto 모드로 시작하니, 지금 모드를 확인하고 `Shift+Tab`으로 바꾸고, 절대 안 되는 일은 거부 규칙으로 막아 두면 돼요.

[IMAGE: 썸네일 | 설명: 정방형 비율, 클로드 코드 권한 모드 사용법을 모드 알기, Shift+Tab으로 바꾸기, 허용·거부 규칙 정하기 세 단계로 나열한 대표 이미지]

"자꾸 허락해 달래요" 하고 한숨 쉬시는 분이 있는가 하면, "예전엔 하나하나 묻더니 요즘은 왜 그냥 고치죠?" 하고 놀라시는 분도 계시죠?
두 고민의 답은 같은 곳에 있습니다. Claude가 어디까지 혼자 해도 되는지 정하는 **권한 모드**예요.

조사일 기준 최신 버전은 새 세션을 묻는 일이 적은 auto 모드로 시작합니다.
그래서 예전 글에서 본 설명과 내 화면이 다를 수 있어요.
이 글에서는 모드 6가지의 차이, `Shift+Tab`으로 바꾸는 법과 플랜 모드, 설정 파일에 허용·거부 규칙을 적는 법까지 순서대로 정리해 드리겠습니다.

지난 글 '클로드 코드 훅 사용법, 입문자도 따라 하는 자동 실행 3단계'에서 알림 훅을 시험할 때 `Shift+Tab`으로 `manual mode on`을 맞춰 보라고 말씀드렸는데요.
그때 바꾼 것이 바로 오늘의 주인공입니다. 시리즈 첫 글 '클로드 코드 핵심 기능 5가지'에서 두 번째로 소개한 권한·플랜 모드를 깊이 풀어 보는 편이기도 해요.

## 🛠️ 시작하기 전에 준비할 것들

* **준비물:** `claude`를 실행해 본 컴퓨터, 연습용 폴더 하나 (git 저장소로 만들어 두면 변경 확인이 쉬워요)
* **소요 시간:** 모드 바꾸기는 키 한 번이면 끝납니다. 규칙을 적고 시험해 보는 데 조금 더 걸려요.
* **난이도:** 입문. 설정 파일에 몇 줄 붙여 넣을 수 있으면 충분합니다.

처음 보는 말부터 짧게 풀어 둘게요.

| 말 | 쉬운 뜻 |
| :-- | :-- |
| 권한 모드 | Claude가 먼저 묻지 않고 해도 되는 일의 범위를 정하는 설정 |
| 상태 표시줄 | 입력창 아래에서 지금 모드를 글자로 보여 주는 줄 (`auto mode on` 등) |
| 허용·거부 규칙 | "이 명령은 묻지 말고 해", "이 파일은 손대지 마"처럼 미리 적어 두는 목록 |
| 분류기 | auto 모드에서 Claude가 하려는 작업을 실행 전에 따로 검토하는 두 번째 AI 모델 |

이 글의 기능 설명은 **조사일(2026-10-27) 기준, Claude Code 2.1.312**와 같은 날 연 공식 문서를 바탕으로 합니다.
모드 이름과 기본값이 버전마다 자주 바뀌는 편이라, `claude --version`으로 내 버전부터 확인해 주세요.

본문의 '직접 해 본 결과'는 같은 날 2.1.312 버전으로 돌린 기록입니다.
앞 글들과 같은 할 일 목록 연습 프로젝트에 가짜 값만 든 `.env`를 두고, 질문을 한 번 보내는 방식(`claude -p`)에 모드를 직접 지정해 실행했어요.

이 방식은 물어볼 사람이 없어서, 대화 화면이라면 "허락할까요?"가 떴을 자리에서 그 작업이 거부됩니다.
auto와 bypassPermissions는 실험 환경의 안전 장치에 막혀 돌려 보지 못했어요. 이 두 모드는 공식 문서 설명으로만 전해 드립니다.

## 1. 클로드 코드 권한 모드가 뭐예요? - 요즘은 왜 덜 물을까요?

공식 문서의 정의는 간단합니다.
클로드 코드 권한 모드는 Claude가 세션 안에서 **먼저 묻지 않고 할 수 있는 작업**을 정해요.

가장 조심스러운 Manual 모드에서는 파일 편집, 셸 명령 실행, 인터넷 접근 같은 대부분의 작업 앞에서 멈추고 묻습니다.
반대로 auto 모드에서는 분류기가 사용자 대신 작업을 살펴보고, 위험해 보이는 것만 막아요.

여기서 입문자분들이 가장 많이 헷갈리는 지점이 나옵니다.
2.1.283 이상 버전에서는 터미널과 VS Code의 새 세션이 요금제와 상관없이 **auto 모드로 시작**해요.
"처음엔 매번 묻는 모드로 시작한다"는 예전 설명은 이제 맞지 않는 셈이죠.

다만 모두가 auto로 시작하는 건 아닙니다.

* 그보다 오래된 버전이거나, 회사 관리자가 auto를 꺼 둔 환경이면 Manual로 시작할 수 있어요.
* auto 자체에도 지원 모델·요금제 조건이 있습니다.
* 그래서 가장 확실한 방법은 입력창 아래 **상태 표시줄 글자**를 직접 보는 것이에요.

새 세션의 시작 모드는 아래 순서로 정해집니다.
앞에서 정한 것이 있으면 뒤의 것은 쓰이지 않아요.

1. 실행할 때 붙인 옵션 (`claude --permission-mode plan` 등)
2. 설정 파일에 적어 둔 기본값 (`permissions.defaultMode`)
3. 클로드 코드에 내장된 기본값 (조사일 기준 터미널·VS Code는 auto)

## 2. [1단계] 모드 알기 - 6가지는 무엇이 다를까요?

공식 이름은 여섯 가지입니다.
상태 표시줄의 기호는 환경에 따라 다르게 보일 수 있으니, 글자 부분으로 구분해 주세요.

| 모드(설정 값) | 상태 표시줄 글자 | 묻지 않고 하는 일 | 잘 맞는 때 |
| :-- | :-- | :-- | :-- |
| `default` (Manual) | `manual mode on` | 읽기만 | 하나하나 직접 보고 싶을 때, 민감한 작업 |
| `acceptEdits` | `accept edits on` | 읽기, 파일 편집, 작업 폴더 안의 간단한 파일 명령 | 검토하면서 코드 고치기를 반복할 때 |
| `plan` | `plan mode on` | 읽기와 탐색 (편집은 계획 승인 뒤) | 바꾸기 전에 둘러보고 계획부터 세울 때 |
| `auto` | `auto mode on` | 백그라운드 안전 검사를 통과한 작업 | 긴 작업, 질문 피로를 줄이고 싶을 때 |
| `dontAsk` | `don't ask on` | 미리 허용한 도구와 작업 폴더 안 읽기만. 물어야 할 일은 전부 거부 | 사람이 지켜보지 않는 자동화 스크립트 |
| `bypassPermissions` | `bypass permissions on` | 거의 모든 작업 | 인터넷이 없는 컨테이너·가상 머신 전용 |

[IMAGE: 비교표 | 설명: 클로드 코드 권한 모드 6가지 비교표. default(Manual), acceptEdits, plan, auto, dontAsk, bypassPermissions의 상태 표시줄 글자와 묻지 않고 하는 일, 잘 맞는 때]

Manual이라고 해서 모든 걸 묻지는 않아요.
작업 폴더 안의 파일 읽기와 검색, `ls`·`cat`이나 `git status` 같은 읽기 전용 명령은 묻지 않고 실행됩니다.

표만 봐서는 감이 잘 안 오시죠?
그래서 같은 요청을 모드만 바꿔 네 번 보내 봤습니다.
요청은 "app.js 맨 아래에 `console.log("ready");` 한 줄을 추가해 줘"였어요.

| 모드 | 거부된 도구 | app.js | Claude의 답 요지 |
| :-- | :-- | :-- | :-- |
| `default` | 편집(Edit) | 그대로 | 쓰기 허락을 받지 못해 못 고쳤다며, 넣을 줄을 안내 |
| `acceptEdits` | 없음 | 1줄 추가 | 맨 아래에 추가했다고 보고 |
| `plan` | 없음 | 그대로 | 플랜 모드라 건드리지 않고 계획만 정리했다고 설명 |
| `dontAsk` | 편집, 셸 명령 | 그대로 | 두 방법 모두 막혀 우회하지 않았다고 설명 |

[IMAGE: 비교표 | 설명: 같은 요청을 권한 모드만 바꿔 실행한 결과표. default와 dontAsk는 거부, acceptEdits는 app.js에 한 줄 추가, plan은 파일을 그대로 두고 계획만 작성]

흥미로웠던 건 `dontAsk`였습니다.
편집이 막히자 Claude가 셸 명령으로 줄을 덧붙이려고 한 번 더 시도했는데, 그것까지 거부됐어요.
"물어야 하는 일은 전부 거부"라는 설명이 그대로 드러난 결과입니다.

`plan`에서는 파일이 바뀌지 않는 대신, 계획이 `~/.claude/plans/` 아래 파일로 저장돼 있었어요.

## 3. [2단계] 바꾸기 - Shift+Tab과 플랜 모드는 어떻게 쓸까요?

모드를 알았다면 이제 상황에 맞게 바꿔 쓸 차례입니다.
방법은 세 가지예요. 세션 중에는 키로, 시작할 때는 옵션으로, 늘 쓰는 기본값은 설정 파일로 정합니다.

### 3-1. 세션 중에는 Shift+Tab

대화 화면에서 `Shift+Tab`을 누를 때마다 모드가 돌아가며 바뀝니다.
auto로 시작한 세션이라면 순서는 아래와 같아요.

1. `auto mode on` (시작 상태)
2. 한 번 누르면 `manual mode on`
3. 두 번째에 `accept edits on`
4. 세 번째에 `plan mode on`
5. 한 번 더 누르면 다시 `auto mode on`

"두 번 누르면 플랜 모드"라는 설명을 보신 적이 있다면, 시작 모드에 따라 횟수가 달라진다는 점을 기억해 두세요.
몇 번 눌렀는지 세기보다 상태 표시줄 글자를 보고 멈추는 편이 정확합니다.

`dontAsk`는 이 순환에 나오지 않고, 실행 옵션으로만 켤 수 있어요.
`bypassPermissions`도 그 모드를 허용한 채 시작한 세션에서만 순환에 끼어듭니다.

[IMAGE: 다이어그램 | 설명: Shift+Tab을 누를 때마다 클로드 코드 권한 모드가 auto, manual, accept edits, plan, 다시 auto로 돌아가는 순환 흐름도]

참고로 제 실험은 대화 화면이 아닌 `claude -p` 방식이었어요.
그래서 `Shift+Tab` 순서는 공식 문서 기준으로 정리했습니다. VS Code에서는 입력창 아래 모드 표시를 눌러 바꿀 수 있다고 안내돼 있어요.

### 3-2. 시작할 때와 기본값 정하기

처음부터 원하는 모드로 열고 싶다면 실행 옵션을 붙입니다.

```bash
claude --permission-mode plan
claude --permission-mode acceptEdits
```

매번 같은 모드로 시작하고 싶다면 `~/.claude/settings.json`에 기본값을 적어 두세요.
아래는 늘 Manual로 시작하게 만드는 예시입니다.

```json
{
  "permissions": {
    "defaultMode": "default"
  }
}
```

(이때 주의할 점이 하나 있어요. `"auto"`와 `"bypassPermissions"`는 프로젝트 폴더의 설정 파일에 적으면 무시됩니다. 내 홈 폴더의 사용자 설정에 적어야 해요.)

### 3-3. 플랜 모드로 계획부터 받기

플랜 모드는 "먼저 계획, 승인 뒤 실행"을 위한 모드입니다.
파일을 읽고 탐색용 명령을 돌리고 계획을 쓰지만, 계획을 승인하기 전까지 소스 파일은 고치지 않아요.
큰 변경을 맡기기 전에 Claude가 무엇을 하려는지 미리 보고 싶을 때 딱 좋습니다.

들어가는 방법은 세 가지예요.

* **키:** `Shift+Tab`으로 `plan mode on`까지 돌리기
* **한 번만:** 요청 앞에 `/plan`을 붙이기
* **처음부터:** `claude --permission-mode plan`으로 시작하기

계획이 준비되면 Claude가 계획을 보여 주고 다음 선택지를 줍니다.

1. **Yes, and use auto mode:** 승인하고 auto 모드로 실행 (auto를 못 쓰는 환경이면 "Yes, auto-accept edits")
2. **Yes, manually approve edits:** 승인하되 편집을 하나씩 확인
3. **No, keep planning:** 플랜 모드에 남아 계획을 더 다듬기

승인하면 플랜 모드가 끝나고, 고른 선택지에 맞는 모드로 바뀌어 편집이 시작돼요.
계획을 직접 고치고 싶다면 `Ctrl+G`로 에디터에서 열 수 있습니다.

[IMAGE: 다이어그램 | 설명: 클로드 코드 플랜 모드 흐름도. 플랜 모드 들어가기, 탐색과 계획 작성, 계획 검토, 승인 선택지(auto로 실행, 편집 하나씩 확인, 계속 계획)에 따라 모드 전환]

> 📌 **전문가 Tip:** 처음 몇 번은 승인 단계에서 "Yes, manually approve edits"를 골라 보세요. 계획과 실제 편집이 어떻게 이어지는지 눈으로 확인하면서 익힐 수 있어요. 익숙해진 뒤에 auto로 맡겨도 늦지 않습니다.

## 4. [3단계] 규칙으로 정하기 - 허용·거부 규칙은 어디에 적을까요?

모드가 "얼마나 알아서 할지"의 큰 틀이라면, 규칙은 "이것만은 이렇게"를 정하는 세부 목록입니다.
규칙은 모드와 따로 작동하고, 종류는 세 가지예요.

* **allow:** 묻지 않고 사용
* **ask:** 쓸 때마다 확인
* **deny:** 사용 금지

평가 순서는 **deny → ask → allow**이고, 먼저 맞는 규칙이 결과를 정합니다.
허용 규칙이 더 구체적이어도 순서는 바뀌지 않아요. 예를 들어 `Bash(aws *)`를 거부해 두면 `Bash(aws s3 ls)`를 허용해도 막힙니다.

먼저 어떤 명령에 허락이 필요한지부터 확인해 봤어요.
Manual 모드에서 `git status`는 묻지 않고 바로 실행됐고, `npm test`는 허락이 필요해 Claude가 시도한 명령 두 건이 모두 거부됐습니다.
읽기만 하는 명령과 프로젝트 스크립트를 돌리는 명령의 차이였죠.

### 4-1. 규칙 적는 법

규칙은 `도구` 또는 `도구(대상)` 모양으로 씁니다.

* `Bash(npm run build)`: 그 명령 정확히 하나
* `Bash(npm run *)`: `npm run`으로 시작하는 명령 전부
* `Read(./.env)`: 현재 폴더의 `.env` 읽기
* `Edit(./app.js)`: `app.js` 고치기

설정 파일에는 이렇게 적어요. 공식 문서의 예시입니다.

```json
{
  "permissions": {
    "allow": ["Bash(npm run lint)", "Bash(npm run test *)"],
    "deny": ["Read(./.env)", "Read(./.env.*)"]
  }
}
```

대화 중에 승인 창에서 "Yes, and don't ask again"을 고르면, 명령 승인은 저장소의 `.claude/settings.local.json`에 규칙으로 저장됩니다.
파일 수정 승인은 세션이 끝날 때까지만 유지돼요.
지금 어떤 규칙이 어느 파일에서 왔는지는 `/permissions`에서 보고, 그 자리에서 추가하거나 지울 수도 있습니다.

### 4-2. 허용 규칙은 어느 파일에 적느냐가 중요해요

앞 글에서 설정 파일 위치를 세 곳으로 나눠 소개해 드렸죠.
그중 `.claude/settings.json`은 저장소에 올려 팀과 함께 쓰고, `.claude/settings.local.json`은 이 프로젝트에서 나만 씁니다.

같은 허용 규칙을 여러 곳에 두고 Manual 모드에서 app.js 한 줄 추가를 요청해 봤어요.

| 규칙을 둔 곳 | 결과 |
| :-- | :-- |
| 공유 `.claude/settings.json`에 `Edit(./app.js)` 허용 | 거부됨 |
| 공유 `.claude/settings.json`에 `Edit` 전체 허용 | 거부됨 |
| 나만 쓰는 `.claude/settings.local.json`에 `Edit(./app.js)` 허용 | 추가됨 |
| 실행 옵션 `--allowedTools "Edit(./app.js)"` | 추가됨 |

공유 파일의 허용 규칙만 듣지 않았습니다.
공식 문서에 따르면 공유 설정의 allow 규칙은 **폴더 신뢰 창을 수락해야** 적용돼요. 제 실험 폴더는 그 확인을 거친 적이 없었으니 설명과 맞는 결과입니다.

이유도 문서에 나와요. 허용 규칙은 할 수 있는 일을 늘리지만, 거부·확인 규칙은 줄이기만 하니 바로 적용해도 안전하다는 거예요.
실제로 팀원이 커밋된 허용 규칙을 받으려면 각자 폴더 신뢰를 수락해야 한다고 공식 문서에 나와 있습니다.
`settings.local.json`에 `Bash(npm test)`를 허용하자, 아까 거부되던 `npm test`도 묻지 않고 실행됐어요.

### 4-3. 거부 규칙은 바로 적용돼요

이번에는 파일 수정을 묻지 않는 `acceptEdits` 모드에서 `.env`를 지켜 봤습니다.

| 설정 | 요청 | 결과 |
| :-- | :-- | :-- |
| 규칙 없음 | `.env` 맨 위에 주석 추가 | 수정됨 |
| 공유 `settings.json`에 `Edit(./.env)` 거부 | 같은 요청 | 거부, `.env` 그대로 |
| 공유 `settings.json`에 `Read(./.env)` 거부 | `.env`의 API_KEY 값 알려 달라 | 거부 |

[IMAGE: 비교표 | 설명: 클로드 코드 허용·거부 규칙 실험 결과표. 공유 settings.json의 허용 규칙은 폴더 신뢰 전이라 거부, settings.local.json 허용은 적용, 공유 settings.json의 거부 규칙은 acceptEdits 모드에서도 바로 .env를 지킴]

허용 규칙과 달리, 거부 규칙은 공유 파일에 있어도 곧바로 적용됐어요.
알아서 고치는 `acceptEdits`에서도 거부 규칙이 이겼고요.
Claude는 수정 요청에는 "권한 설정에서 거부되어 있어 셸 명령으로 우회하지 않았다"고, 읽기 요청에는 "일부러 걸어 둔 제한으로 보여 `cat` 같은 명령으로 돌아가지 않았다"고 답했습니다.

다만 거부 규칙도 만능은 아닙니다.
명령 글자를 보고 판단하는 방식이라 다른 형태로 쓴 같은 명령까지 다 막지는 못해요. 정말 중요한 것은 샌드박스나 훅을 함께 쓰라고 공식 문서가 권합니다.

## 5. 위험한 모드는 언제 쓰나요? - auto·bypassPermissions 주의와 훅의 관계

이 절은 제가 직접 돌려 보지 못한 두 모드를 다루므로, 공식 문서 설명만 옮겨 드릴게요.

### 5-1. auto 모드

auto에서는 분류기가 작업을 실행 전에 검토합니다.
요청 범위를 넘는 일, 모르는 서버를 건드리는 일은 막아요. `curl | bash`처럼 받은 스크립트를 바로 실행하는 것, 강제 푸시, `git reset --hard`, 운영 배포가 기본 차단 예시입니다.

막힌 작업은 알림과 함께 `/permissions`의 Recently denied 목록에 남아요.
연속 3번이나 모두 20번 막히면 auto가 멈추고 다시 묻기 시작합니다.
auto에 들어가면 `Bash(*)`처럼 넓은 허용 규칙은 잠시 꺼진다는 점도 알아 두세요.

그래도 공식 문서는 분명히 선을 긋습니다. 한국어판 표현으로는 "자동 모드는 권한 프롬프트를 줄이지만 안전을 보장하지 않습니다."
대화로 "푸시하지 마"라고 말해 두면 분류기가 참고하긴 하지만, 대화가 압축될 때 사라질 수 있어요. 확실히 막고 싶다면 거부 규칙으로 적어 두는 것이 공식 안내입니다.

### 5-2. bypassPermissions

이 모드는 거의 모든 확인을 건너뜁니다.
공식 문서는 "인터넷 접근이 없는 컨테이너, VM 또는 개발 컨테이너와 같은 격리된 환경에서만" 쓰라고 경고해요. 프롬프트 주입이나 의도하지 않은 작업에 대한 보호도 없다고 적어 두었습니다.

`--dangerously-skip-permissions`도 같은 모드를 켜는 옵션이에요.
이 모드 없이 시작한 세션에서는 중간에 들어갈 수 없습니다. 개인 컴퓨터에서는 쓰지 않는 것이 안전하겠죠.

세 모드를 장단점으로 놓고 보면 이렇습니다. 공식 모범 사례 문서의 비교를 표로 옮겼어요.

| 모드 | 장점 👍 | 단점 👎 |
| :-- | :-- | :-- |
| Manual | 모든 작업을 내가 직접 확인 | 질문이 쌓이면 읽지 않고 승인하게 되고, 자리를 비우면 멈춤 |
| auto | 흐름이 끊기지 않고 위험한 일은 걸러 줌 | 판단하는 쪽도 모델이라 틀릴 수 있음 |
| bypassPermissions | 제약 없이 빠름 | 보호 장치가 없어 일회용 격리 환경에서만 의미 |

### 5-3. 훅과는 어떤 관계일까요?

앞 글의 훅과 오늘의 모드가 만나는 지점이 여기입니다.
`PreToolUse` 훅은 권한 모드를 확인하기 **전에**, 모든 모드에서 실행돼요.

그래서 훅이 막은 작업은 auto는 물론 bypassPermissions에서도 막힌다고 공식 문서가 밝히고 있습니다.
반대로 훅이 "허용"이라고 답해도 설정의 거부 규칙을 넘지는 못해요.
앞 글에서 만든 `.env` 보호 훅도 공식 문서 설명대로라면 모드를 바꿔도 계속 지켜 줍니다. (auto·bypass에서의 확인은 제가 직접 하지 못했어요.)

[IMAGE: 다이어그램 | 설명: Claude가 도구를 쓰기 전 확인 순서 흐름도. PreToolUse 훅, 거부·확인·허용 규칙, 클로드 코드 권한 모드 순으로 거치며 훅과 거부 규칙은 모든 모드에서 유지됨]

정리하면 CLAUDE.md는 Claude에게 하는 **부탁**이고, 권한 규칙과 훅은 클로드 코드 프로그램이 지키게 하는 **강제**예요.
공식 문서도 프롬프트나 CLAUDE.md는 Claude가 하려는 일을 바꿀 뿐, 허용 범위 자체는 바꾸지 않는다고 짚습니다.

> 📌 **전문가 Tip:** 입문자라면 기본 auto를 그대로 쓰되, `.env`나 `git push`처럼 절대 안 되는 일은 거부 규칙에 넣어 두세요. 큰 변경은 플랜 모드로 계획부터 받고요. 이 세 가지만 지켜도 편함과 안심을 함께 챙길 수 있습니다.

## 6. 자주 묻는 질문 - 이런 경우엔 어떻게 하나요?

**Q. 지금 무슨 모드인지 어떻게 아나요?**
입력창 아래 상태 표시줄을 보세요.
`auto mode on`, `manual mode on`처럼 글자로 나옵니다.

**Q. 예전처럼 매번 묻게 하고 싶어요.**
세션 중에는 `Shift+Tab`으로 `manual mode on`에 맞추면 됩니다.
늘 그렇게 쓰려면 3-2처럼 `~/.claude/settings.json`에 `"defaultMode": "default"`를 적어 두세요.

**Q. 반대로 질문이 너무 많아서 피곤해요.**
자주 쓰는 안전한 명령을 허용 규칙에 넣는 것이 첫 번째 방법이에요.
공식 모범 사례는 최근 기록을 보고 읽기 전용 명령을 허용 목록에 넣어 주는 `/fewer-permission-prompts` 명령도 소개합니다.

**Q. "don't ask again"을 눌렀는데 또 물어요.**
그 승인은 나만 쓰는 로컬 파일의 허용 규칙으로 저장됩니다.
프로젝트나 관리 설정에 같은 작업의 ask 규칙이 있으면 그쪽이 먼저라, 계속 묻게 돼요.

**Q. `claude -p`로 실행하면 작업이 자꾸 거부돼요.**
버전과 환경에 따라 `-p`가 Manual로 시작할 수 있다고 공식 문서와 변경 이력에 나와 있어요.
`--permission-mode`로 모드를 직접 지정하거나 `--allowedTools`로 필요한 도구를 허용해 보세요. 제 실험도 모두 모드를 직접 지정해서 돌렸습니다.
