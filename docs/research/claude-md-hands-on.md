# 리서치 노트: CLAUDE.md 직접 써 보기

- 조사일: 2026-10-27
- 기준 시점: 2026-10-27. 공식 문서 페이지를 이날 열어 확인했다. 두 페이지 모두 발행·수정일 표기가 없어 "조사일 기준 공개 내용"으로 쓴다. 문서에 버전 표기(v2.1.xxx)가 많으니 독자 버전에 따라 기능이 다를 수 있다.
- 목적/독자: 네이버 블로그 정보·리뷰형 글의 근거. 독자는 Claude Code 입문자이고, 읽고 나서 CLAUDE.md를 직접 만들 수 있게 하는 것이 목표.
- [가정] 독자는 터미널에서 `claude`를 실행해 본 정도의 입문자다. 영어 원문은 한국어로 요약했고 인용은 짧게만 했다.

## 1. 결론 요약

- CLAUDE.md는 "세션을 시작할 때마다 Claude가 읽는, 내가 직접 쓰는 지침 파일"이다. Claude Code 세션은 매번 새 컨텍스트로 시작하므로 매번 다시 설명할 내용을 여기에 적어 둔다 [사실] ([1]).
- 프로젝트용은 `./CLAUDE.md` 또는 `./.claude/CLAUDE.md`, 개인 전체용은 `~/.claude/CLAUDE.md`, 개인+프로젝트용은 `./CLAUDE.local.md`다. `/init`으로 초안을 만들고 `/memory`로 열어 고친다 [사실] ([1]).
- 잘 쓰는 법은 "짧게(파일당 200줄 미만 권장), 구체적으로(검증 가능한 문장), 구조화해서(헤더+목록), 상충 없이"다. 코드를 읽으면 알 수 있는 내용(구조 설명 등)보다 Claude가 모르는 것(명령, 함정, 팀 결정)을 적는다 [사실] ([1], [2]).
- CLAUDE.md는 강제가 아니라 맥락이다. 예외 없이 지켜야 하는 규칙은 훅(hook)·권한 거부 규칙으로 옮기라는 것이 공식 입장이다 [사실] ([1], [2]).
- 이 저장소의 CLAUDE.md는 67줄로 권장 범위 안이다. 명령어·함정·규칙 위주라 좋은 사례지만, 구조 설명이 많은 점과 에이전트 목록이 실제 파일과 어긋난 점은 짚을 만하다 (6절, [저장소 사실]).

## 2. 질문별 조사 결과

### Q1. CLAUDE.md가 무엇이고 왜 필요한가?

- [사실] 각 Claude Code 세션은 새 컨텍스트 창으로 시작한다. 지식을 세션 사이에 넘기는 장치는 둘이다. 내가 쓰는 CLAUDE.md, Claude가 스스로 쓰는 자동 메모리(auto memory) ([1]).
- [사실] 비교표 ([1]):

| 구분 | CLAUDE.md | 자동 메모리 |
| :- | :- | :- |
| 작성자 | 나 | Claude |
| 내용 | 지침과 규칙 | 배운 점과 패턴 |
| 범위 | 프로젝트·사용자·조직 | 저장소별(워크트리끼리 공유) |
| 로드 | 매 세션 | 매 세션(MEMORY.md 앞 200줄 또는 25KB) |
| 용도 | 코딩 표준, 워크플로, 프로젝트 구조 | 내 선호, 내가 해 준 교정, 코드에서 알 수 없는 맥락 |

- [사실] 자동 메모리는 로컬 세션에서 기본으로 켜져 있고, `/memory`에서 켜고 끌 수 있다. 저장 위치는 `~/.claude/projects/<project>/memory/`이며 같은 기기에서만 유효하고 다른 기기와 공유되지 않는다 ([1]).
- [사실] 자동 메모리에는 "항상 pnpm을 써라" 같은 말을 하면 저장된다. CLAUDE.md에 넣으려면 "CLAUDE.md에 추가해 줘"라고 직접 말하거나 `/memory`로 직접 편집해야 한다 ([1]).
- [사실] CLAUDE.md에 추가할 때: 같은 실수를 두 번째 했을 때, 코드 리뷰에서 "이건 알았어야 한다"가 나왔을 때, 지난 세션에 쓴 교정을 또 쓸 때, 새 팀원도 같은 맥락이 필요할 때 ([1]).
- [사실] 새 `/init`·`/memory` 외에 Claude가 읽는 파일로 `AGENTS.md`도 있다. 저장소에 `AGENTS.md`만 있고 CLAUDE.md가 없으면 `AGENTS.md`를 읽는다(v2.1.277 이상). CLAUDE.md가 있으면 기본은 CLAUDE.md만 읽는다 ([1]).
- 신뢰도: 높음 (A 등급 출처 [1], [2] 일치. 다만 두 문서 모두 같은 발행처라 "서로 다른 독립 출처"는 아님).

### Q2. 어디에 어떻게 만드나?

- [사실] 위치와 범위 (로드 순서는 넓은 범위에서 좁은 범위로, 프로젝트 지침이 사용자 지침보다 뒤에 나온다) ([1]):

| 범위 | 위치 | 공유 |
| :- | :- | :- |
| 관리형 정책(조직) | Linux/WSL `/etc/claude-code/CLAUDE.md`, macOS `/Library/Application Support/ClaudeCode/CLAUDE.md`, Windows `C:\Program Files\ClaudeCode\CLAUDE.md` | 조직 전체 |
| 사용자 | `~/.claude/CLAUDE.md` | 나, 모든 프로젝트 |
| 프로젝트 | `./CLAUDE.md` 또는 `./.claude/CLAUDE.md` | 팀(버전 관리) |
| 로컬 | `./CLAUDE.local.md` (`.gitignore`에 추가) | 나, 현재 프로젝트 |

- [사실] 로드 방식: 작업 디렉터리와 그 위쪽 모든 디렉터리의 CLAUDE.md·CLAUDE.local.md가 시작 때 로드되고, 모두 이어 붙여져(덮어쓰지 않음) 컨텍스트에 들어간다. 파일시스템 루트에서 작업 디렉터리 순으로 배치되어 가까운 파일이 뒤에 온다. 하위 디렉터리의 CLAUDE.md는 Claude가 그 디렉터리의 파일을 읽거나 편집할 때 그때 로드된다 ([1]).
- [사실] `/init`은 코드베이스를 분석해 빌드 명령, 테스트 방법, 발견한 규칙이 담긴 초안을 만든다. 이미 CLAUDE.md가 있으면 덮어쓰지 않고 개선안을 제안한다. 환경변수 `CLAUDE_CODE_NEW_INIT=1`을 켜면 CLAUDE.md·스킬·훅 중 무엇을 만들지 묻는 다단계 대화형 방식이 된다 ([1]).
- [사실] `/init`은 Cursor 규칙(`.cursor/rules/`, `.cursorrules`)과 Copilot 규칙(`.github/copilot-instructions.md`)을 읽어 반영한다 ([1]).
- [사실] `/memory`: CLAUDE.md, CLAUDE.local.md 등 메모리 파일 목록을 보여 주고(아직 없는 사용자·프로젝트 CLAUDE.md도 표시), 선택하면 편집기에서 열거나 새로 만든다. 자동 메모리 토글과 폴더 열기도 여기에 있다 ([1]).
- [사실] 가져오기(import): `@path/to/파일` 문법. 상대·절대 경로 모두 가능, 상대 경로는 "가져오는 파일" 기준, 재귀 가져오기는 최대 4단계. 백틱 코드로 감싼 `@README`는 가져오지 않는다. 공식 예시는 `See @README for project overview and @package.json ...` ([1]).
- [사실] 가져오기는 정리에는 도움이 되지만 컨텍스트 비용을 줄이지는 않는다. 가져온 파일도 함께 로드되기 때문이다 ([1]).
- [사실] 작업 디렉터리 밖을 가리키는 가져오기(예: `@~/...`)는 프로젝트에서 처음 만나면 승인 창이 뜬다 ([1]).
- [사실] `.claude/rules/`: 주제별 `.md` 파일(예: `testing.md`, `security.md`)을 둔다. 하위 폴더까지 재귀 탐색한다. `paths` 프런트매터가 없는 규칙은 시작 때 `.claude/CLAUDE.md`와 같은 우선순위로 로드되고, `paths: ["src/api/**/*.ts"]`처럼 글롭 패턴을 주면 해당 파일 작업 때만 로드된다. 규칙 파일에서 Claude Code가 읽는 프런트매터 필드는 `paths` 하나뿐이다 ([1]).
- [사실] 개인 규칙은 `~/.claude/rules/`에 둔다. 사용자 규칙이 프로젝트 규칙보다 먼저 로드되며 어느 쪽도 상대를 덮어쓰지 않으므로, 충돌하면 어느 쪽을 따를지 모른다 ([1]).
- [사실] 본문 속 블록 수준 HTML 주석 `<!-- 메모 -->`은 컨텍스트에 주입되기 전에 제거된다. 사람용 메모를 토큰 소모 없이 남길 수 있다 ([1]).
- [사실] 대형 저장소에서 남의 CLAUDE.md를 빼려면 `claudeMdExcludes` 설정을 쓴다 ([1]).
- 신뢰도: 높음.

### Q3. 무엇을 적고 무엇을 적지 말아야 하나?

- [사실] 공식 "효과적인 지침" 원칙 ([1]):
  - 크기: 파일당 200줄 미만을 목표. 길면 컨텍스트를 더 쓰고 준수율이 떨어진다. 일부에만 해당하는 내용은 경로 한정 규칙으로 옮긴다.
  - 구체성: 검증 가능한 문장. "2칸 들여쓰기를 쓴다"(O) / "코드를 잘 정리한다"(X) 식. 공식 예시 3개: "Use 2-space indentation", "Run `npm test` before committing", "API handlers live in `src/api/handlers/`".
  - 구조: 마크다운 헤더와 글머리표로 묶는다. 빽빽한 문단보다 따르기 쉽다.
  - 일관성: 두 지침이 모순되면 Claude가 임의로 하나를 고를 수 있다. 하위 폴더 CLAUDE.md와 `.claude/rules/`까지 주기적으로 점검한다.
- [사실] 베스트 프랙티스 문서는 "Claude가 코드만 봐서는 알 수 없는 것"만 적으라고 한다: ① 이 저장소에서 작업을 확인하는 정확한 테스트·타입체크·린트 명령과 파일 하나만 돌리는 법, ② 코드가 오해를 부르는 곳(곳곳에 있지만 새 코드에는 쓰면 안 되는 옛 패턴 등), ③ 저장소에 없는 결정(팀이 정한 에러 헬퍼, 배포 방식), ④ 두 번 이상 교정한 것 ([2]).
- [사실] 같은 문서의 "이제 하지 않아도 되는 것" 표에는 "CLAUDE.md에 아키텍처·파일 구조 설명 적기"가 있다. 이유는 "Claude가 저장소를 직접 읽는다. 거기 없는 것만 적어라"이다 ([2]).
- [사실] 강조 표현(IMPORTANT, 대문자)을 덧붙여도 해결되지 않는다. 최신 모델은 평이하게 쓴 문장을 따르고, 강조를 쌓으면 규칙을 과적용하는 경향이 있다. 놓치는 이유는 파일이 길어서 줄이 묻히거나, 예외 없는 규칙이라 훅이 필요하기 때문이라는 설명이다 ([2]).
- [사실] 여러 단계 절차나 한 부분에만 해당하는 내용은 CLAUDE.md가 아니라 스킬(skill) 또는 경로 한정 규칙으로 옮기라고 한다. 스킬은 필요할 때만 전체 내용을 읽으므로 컨텍스트 부담이 적다 ([1], [2]).
- [사실] 개인 선호는 `CLAUDE.local.md`(gitignore)에 둔다 ([1], [2]).
- [사실] 점검 도구: `/doctor`는 코드에서 알 수 있는 내용(디렉터리 구조, 의존성 목록, 아키텍처 개요)을 잘라내자고 제안하고, 함정·이유·기본값과 다른 규칙은 남긴다. `/doctor prompt-audit`은 옛 모델용 지침, 없는 파일·명령 참조, 서로 모순되는 파일을 찾아 보고서로 알려 준다. 적용은 사용자가 요청해야 한다(v2.1.283 이상 필요) ([1]).
- [사실] 길이 경고: 권장 길이를 넘는 지침 파일이 있으면 시작 때와 `/status`에서 경고가 뜬다. 파일 4 MiB 초과는 아예 로드되지 않는다. 하위 폴더·경로 한정 파일에는 별도 글자 수 한도(200K 컨텍스트 40,000자 등)가 있다 ([1]).
- [해석] 흔한 실수를 정리하면: 길게 쓰기, 모호하게 쓰기, 코드에서 알 수 있는 구조를 장황하게 쓰기, 상충하는 지침, 강조어 남발, 지켜져야만 하는 규칙을 CLAUDE.md에만 적기, 오래된 내용 방치. 모두 [1]·[2]의 개별 설명을 내가 묶은 것이다.
- 신뢰도: 높음. 단 "200줄"은 공식 권고 수치이고 제3자 글은 100줄 등 제각각이라(검색 결과 요약 기준, 열어 보지 않음) 공식 수치만 쓴다.

### Q4. 잘 적용되고 있는지 어떻게 확인하나? 한계와 대안은?

- [사실] 로드 확인: 세션에서 `/context`를 실행해 **Memory files** 목록에 파일이 있는지 본다. 목록에 없으면 Claude가 볼 수 없다 ([1], [2]).
- [사실] 하위 폴더 CLAUDE.md는 시작 때 로드되지 않아 Memory files에 안 보인다. 로드되면 터미널에 `Loaded` 줄이 나온다. 테스트하려면 그 폴더의 파일을 읽게 해 본다 ([1]).
- [사실] `/memory` 목록으로도 어떤 파일이 있는지 확인할 수 있다 ([1]).
- [사실] 지켜지지 않을 때 점검 순서(공식): 로드 여부 확인 → 위치 확인 → 지침을 더 구체적으로 → 파일 간 상충 확인 → Claude Code가 자체로 넣는 커밋·PR 지침과 충돌하는지 확인 ([1]).
- [사실] `InstructionsLoaded` 훅으로 어떤 CLAUDE.md·규칙이 언제 왜 로드됐는지 기록할 수 있다 ([1]).
- [사실] 한계: CLAUDE.md는 시스템 프롬프트가 아니라 그 뒤의 사용자 메시지로 전달된다. Claude가 읽고 따르려 하지만 엄격한 준수 보장은 없다. 특히 모호하거나 상충하는 지침에서 그렇다 ([1]). 베스트 프랙티스 문서는 이를 "비결정적(모델이 판단)" 대 "결정적(하니스가 실행)"으로 나눈다 ([2]).
- [사실] 대안: 반드시 특정 시점에 실행해야 하는 일(커밋 전, 파일 편집 후)은 훅(hook)으로 쓴다. 훅은 정해진 생명주기 시점에 셸 명령으로 실행되며 Claude의 판단과 무관하게 적용된다. 공식 예: "`.env` 읽지 마라", "편집 후 포매터 실행", "migrations 폴더 건드리지 마라"는 CLAUDE.md에서 훅(PostToolUse/PreToolUse)이나 거부 규칙으로 옮길 후보로 제시된다. `PreToolUse` 훅은 행동을 차단할 수 있다 ([1], [2]).
- [사실] 공식 지침: 훅은 예외가 0인 규칙에만 쓰고 "named export 선호" 같은 선호는 CLAUDE.md에 둔다. 강제 장치를 너무 늘리지 말라는 경고도 있다 ([2]).
- [사실] `/compact` 후에도 프로젝트 루트 CLAUDE.md는 디스크에서 다시 읽혀 유지된다. 대화로만 준 지침은 사라질 수 있으므로 CLAUDE.md에 적어야 지속된다 ([1]).
- 신뢰도: 높음.

### Q5. 입문자를 위한 최소 템플릿

## 6. 이 저장소의 실제 사례 [저장소 사실]

> 이 절의 근거는 웹이 아니라 저장소 파일 `/home/user/claude-code-version/CLAUDE.md`와 그 파일이 언급하는 경로의 존재 여부 확인이다. 이유(why)는 파일에 적혀 있지 않은 경우 "[해석]"으로 표시했다. 작성 경위(누가 어떻게 썼는지, `/init` 사용 여부)는 파일만으로 알 수 없어 쓰지 않았다.

### 파일 개요
- [저장소 사실] 위치는 저장소 루트 `CLAUDE.md`, 한국어, 총 67줄(공백 줄 포함, 비어 있지 않은 줄 51개). 공식 권장 200줄 미만 안에 있다. 3줄째 첫 문장은 "This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository."로 영어 한 문장이다.
- [저장소 사실] 섹션 구성: `저장소 개요` / `백엔드 명령` / `웹` / `백엔드 구조` / `구조` / `에이전트 파일 작성 규칙` (6개 `##` 헤더).

### 무엇을 적었나 (섹션별)
- 저장소 개요: 저장소가 담는 두 가지(서브에이전트, 식단 기록 앱)와 기준 문서 위치.
- 백엔드 명령: 가상환경 생성, 개발 서버, 전체/단일 테스트, 린트 명령을 코드 블록으로. 파일 안에 함정도 있다: "pyproject addopts에 -q가 있어 -q를 또 주면 요약 줄이 사라짐". 이는 공식이 말하는 "확인 명령 + 알기 어려운 함정"에 해당한다 ([2]와 대응, [해석]).
- 웹: 빌드 도구가 없다는 점, 종단 테스트 명령과 "포트가 이미 쓰이면 실패" 주의, `innerHTML` 금지(이유: 토큰이 `localStorage`에 있어 XSS가 곧 토큰 탈취), 확인 창은 `confirm()` 대신 `askConfirm`(이유: iframe에서 `confirm()`이 항상 false). 문구 원칙: 기록하지 않은 날을 실패·미달로 표현하지 않는다.
- 백엔드 구조: 계층(api → services → repositories), 인증 방식, 시간대 기준, 마이그레이션, 미들웨어 순서와 "`exception_handler(Exception)`을 다시 추가하지 않는다(uvicorn이 traceback을 찍는다)", "순서를 바꾸면 `tests/test_qa_cors_error_responses.py`, `tests/test_cors.py`가 잡는다", 제품 원칙상 칼로리·점수 필드를 API에 추가하지 않는다.
- 구조: 서브에이전트 정의 위치와 각 에이전트의 한 줄 역할, 블로그 가이드 문서와 이미지 캡처 명령.
- 에이전트 파일 작성 규칙: 프론트매터 필드, `description` 작성 시 YAML 콜론 함정, 한국어 보고서 선호, 프론트매터 검증 명령.

### 왜 이렇게 적은 것으로 보이나 [해석]
- "하지 말 것 + 이유" 형태의 줄(`innerHTML` 금지, `exception_handler(Exception)` 재추가 금지, `confirm()` 금지)이 많다. 이런 줄은 코드만 봐서는 이유를 알기 어렵고 한 번 어기면 되돌리기 번거로운 규칙이라, 공식이 말하는 "코드가 오해를 부르는 곳·저장소에 없는 결정"에 맞는다 ([2]).
- 요구사항을 바꾸면 PRD와 테스트를 함께 고치라는 줄, API 응답이 바뀌면 `demo-api.js`도 고치라는 줄은 파일 간 연동 규칙이다. 코드에서 즉시 드러나지 않는 연동이라 적은 것으로 보인다.
- 수정 후 프론트매터 검증 명령을 그대로 넣은 것은 "작업을 확인하는 정확한 명령"에 해당한다 ([2]).

### 짚을 점 (입문자 학습 포인트)
- [저장소 사실] 길이는 67줄이라 양호하지만 `백엔드 구조` 섹션의 한 줄이 매우 길다(예: 미들웨어 순서 줄, 보안 미들웨어 줄). 구조화는 헤더+목록으로 되어 있어 공식의 "구조" 원칙에 맞다.
- [해석] "구조" 섹션과 `백엔드 구조`의 계층·디렉터리 설명은 코드를 읽어도 알 수 있는 부분이 섞여 있다. 공식은 아키텍처·파일 구조 설명은 Claude가 직접 읽으니 줄이라고 권한다 ([2]). 입문자에게는 "이 부분은 `/doctor`가 줄이자고 제안할 수 있는 후보"로 소개할 수 있다(실제 `/doctor` 실행 결과는 확인하지 않았다).
- [저장소 사실] 오래된 내용의 예: `구조` 섹션의 에이전트 목록은 `code-reviewer`, `product-manager`, `backend-developer`, `qa-engineer`, `researcher`, `writer`, `assembler` 7개이나, 실제 `.claude/agents/`에는 `image-maker.md`도 있다(조사일 Glob 확인). 즉 목록이 파일 실제 상태보다 한 항목 뒤처져 있다. "CLAUDE.md는 낡을 수 있다"는 사례로 쓸 수 있다. 단 `image-maker`가 일부러 빠진 것인지는 알 수 없다.
- [저장소 사실] 이 파일이 언급하는 경로 중 확인한 것(`tools/make_blog_images.py`, `tools/build_preview.py`, `web/tools/build_demo.py`, `web/tests/e2e.mjs`, `docs/guides/` 3개 문서, `backend/app/api/ratelimit.py`, `backend/tests/test_qa_cors_error_responses.py`, `docs/prd/easy-meal-log.md`)은 모두 실제로 존재한다. 이 외 경로(테스트 `test_cors.py` 등)는 확인하지 않았다.
- [저장소 사실] 이 파일은 지침 파일 하나에 코드 개발 규칙과 블로그 에이전트 설명이 함께 들어 있다. 커지면 `.claude/rules/`(예: 백엔드 전용에 `paths: ["backend/**"]`)로 나눌 수 있다는 점이 공식 기능과 이어지는 [해석]이다. 실제로 나눈 적은 없다.
- 확인하지 않은 것: 이 파일이 실제 세션에서 얼마나 잘 지켜졌는지, `/context`로 로드를 확인했는지는 이 조사에서 확인하지 않았다. 효과를 서술하는 문장은 필자가 직접 겪은 경우에만 쓸 것.

## 8. 확인하지 못한 자료

- 검색(WebSearch)으로 나온 제3자 글(medium, crystl.dev, thepromptshelf.dev, uxplanet 등)은 원문을 열지 않았고 일부는 회원 전용이다. 근거로 쓰지 않았다(등급 C 이하로 간주).
- 위 4개 보조 공식 페이지(hooks-guide 등)는 열지 않았다.
- 공식 문서의 발행·수정일은 페이지에 표시되지 않아 확인하지 못했다.
- 실제 `/init`·`/context`·`/doctor` 실행은 하지 않았다.

## 용어 설명

- 컨텍스트(context): Claude가 한 번에 "보고 있는" 대화와 파일 내용의 범위. 길수록 한 줄 한 줄이 차지하는 주의가 줄어든다.
- 훅(hook): Claude의 작업 중 정해진 시점(파일 편집 전후, 작업 종료 직전 등)에 자동 실행되는 내 명령. Claude의 판단과 상관없이 실행된다.
- 프런트매터(frontmatter): 마크다운 파일 맨 위 `---` 사이에 적는 설정 줄.
- 글롭 패턴(glob): `src/**/*.ts`처럼 파일 경로를 와일드카드로 지정하는 표기.
- 가져오기(import): CLAUDE.md 안에 `@파일경로`를 적어 다른 파일 내용을 함께 읽게 하는 기능.
- 스킬(skill): 필요할 때만 불러오는 작업 절차 모음 파일.
- 자동 메모리(auto memory): Claude가 내 교정과 선호를 스스로 메모해 두는 기능.
- 컴팩트(`/compact`): 긴 대화를 요약해 컨텍스트를 줄이는 명령.
