# 간편 식단 기록 앱 (Easy Meal Log) PRD

| 항목 | 내용 |
|---|---|
| 상태 | 초안 |
| 작성일 · 최종 수정일 | 2026-10-26 · 2026-10-26 (미결 사항 결정 반영) |

## 1. 요약
다이어트 중 식단 기록을 정확한 칼로리와 수치 없이 "무엇을 먹었는지 한 줄"로 끝낼 수 있게 해 주는 앱이다.
식단 기록이 부담스러워 기록을 그만두고, 그 결과 다이어트까지 흐트러지는 사람을 위해 만든다.
기록의 정확도보다 기록을 계속하는 것을 우선해, 기록을 꾸준히 하면 다이어트에 도움이 된다는 가설을 검증한다.

## 2. 배경과 문제

### 사용자가 겪는 문제
기획자(사용자)가 제시한 배경에 따르면, 기존 식단 기록 방식은 현대인에게 스트레스 요인이 되고, 다음 세 가지 부담 때문에 기록을 포기하게 된다.

| # | 문제 | 기존 방식에서 생기는 이유 |
|---|---|---|
| P1 | 정확한 칼로리를 기록해야 한다는 압박 | 음식마다 칼로리를 찾아 입력해야 기록이 끝난다 |
| P2 | 수시로 기록해야 한다는 강박 | 끼니마다 바로 기록하지 않으면 기록이 끊긴 것처럼 느껴진다 |
| P3 | 수치 하나하나가 정확해야 한다는 부담 | 중량(g), 영양소 등 모르는 값을 채워야 한다 |

결과: 기록 포기 → 자기 식습관을 돌아볼 근거가 사라짐 → 다이어트에 지장.

근거: 현재 근거는 기획자의 관찰뿐이다. 사용자 인터뷰나 설문 같은 검증 자료는 아직 없다(미결 사항 Q7).

### 왜 지금 해결해야 하는가
- 정해진 기한은 없다(Q1 결정). 일정 압박보다 핵심 원칙을 지키는 품질을 우선한다.

### 해결 방향 (제품 원칙)
아래 원칙은 모든 기능 요구사항이 따라야 하는 기준이다.

1. **한 가지만 입력하면 기록 끝**: 필수 입력은 "무엇을 먹었는지" 텍스트 하나뿐이다. (P1, P3 대응)
2. **숫자를 요구하지 않는다**: 칼로리, 중량, 영양소 입력란을 두지 않는다. 양은 "적게/보통/많이" 같은 대략적 선택지로만 받는다. (P1, P3 대응)
3. **나중에 몰아서 기록해도 된다**: 지난 날짜의 기록을 자유롭게 추가할 수 있고, 기록하지 않은 날을 실패로 표시하지 않는다. (P2 대응)
4. **판단하지 않는다**: 기록에 점수, 경고, "목표 초과" 같은 평가를 붙이지 않는다. (P1, P2 대응)

## 3. 목표와 성공 지표

모든 목표치는 비교 기준(기존 앱 사용 경험, 경쟁 제품 수치)이 없어 정한 `[가정]` 값이다. 베타 테스트(M3) 결과를 보고 다시 정한다.

| ID | 목표 | 지표 | 목표치 | 측정 방법 |
|---|---|---|---|---|
| G1 | 기록 한 건에 드는 수고를 최소화한다 | 기록 화면 진입부터 저장까지 걸린 시간의 중앙값 | 10초 이하 `[가정]` | 클라이언트 이벤트 로그(진입·저장 시각). 클라이언트 단계(M2)에서 측정 |
| G2 | 기록을 포기하지 않고 이어가게 한다 | 가입 후 4주차에 주 3일 이상 기록한 사용자 비율 | 40% 이상 `[가정]` | 서버에 저장된 기록의 날짜별 집계 |
| G3 | 기록에 대한 심리적 부담을 줄인다 | "식단 기록이 부담스럽다" 5점 척도 문항 점수 | 가입 시점 대비 4주 후 평균 1점 이상 감소 `[가정]` | 베타 테스터 대상 앱 내 또는 외부 설문 |
| G4 | 다이어트에 도움이 된다 | "식습관을 돌아보는 데 도움이 됐다" 5점 척도 문항 점수 | 평균 4점 이상 `[가정]` | 베타 테스터 대상 설문 |

G4를 체중 변화로 측정하지 않는 이유: MVP는 체중을 기록하지 않으며(8절), 4주 안팎의 베타 기간에 체중 변화를 앱 효과로 볼 근거가 약하다.

### 목표가 아닌 것
- 정확한 칼로리·영양소 계산과 관리
- 의학적 체중 관리, 식이 처방, 질환 관리
- 운동 기록, 체중 기록 등 식단 이외의 건강 데이터 관리
- 다른 사용자와의 공유나 커뮤니티 기능

## 4. 대상 사용자

대상은 식단 기록에 부담을 느끼는 현대인 전체다(Q2 결정). 아래 유형은 모두 대상이며, 핵심 문제를 가장 직접 겪는 A를 메시지와 기능 판단의 1순위로 둔다.

| 유형 | 상황 | 필요 |
|---|---|---|
| A. 기록 포기 경험자 `[가정]` | 칼로리 기록 앱을 써 봤지만 입력이 번거로워 며칠 만에 그만둔 적이 있다 | 정확도 부담 없이 다시 기록을 시작하고 싶다 |
| B. 바쁜 직장인·학생 `[가정]` | 끼니마다 앱을 열 여유가 없다 | 저녁이나 다음 날 몰아서 기록해도 괜찮기를 바란다 |
| C. 처음 다이어트하는 사람 `[가정]` | 칼로리나 영양 지식이 거의 없다 | 숫자를 몰라도 "무엇을 얼마나 먹었는지" 돌아볼 수 있기를 바란다 |

## 5. 사용자 스토리
- US-1: 다이어트 중인 사용자로서, 칼로리를 찾아보지 않고도 기록을 끝내기 위해 먹은 음식을 한 줄로만 적고 싶다. (P1, P3)
- US-2: 사용자로서, 정확한 양을 몰라도 식사량을 남기기 위해 "적게/보통/많이" 중 하나만 고르고 싶다. 고르지 않아도 기록은 저장돼야 한다. (P3)
- US-3: 바쁜 사용자로서, 끼니마다 앱을 열지 않아도 되도록 지난 끼니나 어제 먹은 것을 나중에 몰아서 기록하고 싶다. (P2)
- US-4: 사용자로서, 잘못 적은 기록을 바로잡기 위해 기록을 고치거나 지우고 싶다.
- US-5: 사용자로서, 내 식습관을 돌아보기 위해 하루 또는 한 주 동안 먹은 것을 날짜별로 보고 싶다. (G4)
- US-6: 비슷한 음식을 자주 먹는 사용자로서, 같은 내용을 다시 타이핑하지 않도록 최근에 적은 메뉴를 골라 바로 기록하고 싶다. (G1)
- US-7: 사용자로서, 한 주를 돌아볼 때 "몇 번 실패했는지"가 아니라 "며칠 기록했는지"를 보고 싶다. (P2, G2)
- US-8: 사용자로서, 내 식단 정보를 다른 사람이 볼 수 없고, 원하면 계정과 기록을 모두 지울 수 있기를 바란다.

### 6.2 다루는 데이터 항목

API 경로, DB 스키마, 필드 이름, 저장소 종류는 개발자가 정한다. 아래는 저장하고 주고받아야 하는 정보의 내용과 제약이다.

**식사 기록(Meal Entry)**

| 항목 | 필수 여부 | 내용과 제약 |
|---|---|---|
| 기록 식별자 | 시스템 생성 | 기록 하나를 가리키는 고유 값 |
| 소유자 | 시스템 설정 | 기록을 만든 사용자. 요청 본문이 아니라 인증된 사용자로 정한다 |
| 먹은 것 (설명) | **필수** | 자유 텍스트. 앞뒤 공백을 제거한 뒤 1자 이상 200자 이하 `[가정]`. 줄바꿈 허용 여부는 개발자 판단 |
| 식사 날짜 | 선택 (기본값: 사용자의 오늘) | 기록이 속한 날짜(연-월-일). 사용자의 현지 날짜 기준이다. 미래 날짜는 거부한다. 과거 날짜 제한은 두지 않되, 서비스 출시일 이전 등 명백히 잘못된 값의 처리 기준은 개발자 판단 |
| 끼니 구분 | 선택 | `아침`, `점심`, `저녁`, `간식` 중 하나 또는 비어 있음. 비어 있어도 된다 |
| 식사량 | 선택 | `적게`, `보통`, `많이` 중 하나 또는 비어 있음. 숫자(g, kcal)는 받지 않는다 |
| 메모 | 선택 | 자유 텍스트, 500자 이하 `[가정]`. 기분, 상황 등 |
| 생성 시각, 수정 시각 | 시스템 생성 | 정렬과 동기화용 |

- 칼로리, 중량, 영양소 항목은 두지 않는다(제품 원칙 2).
- 끼니 구분과 식사량의 선택지는 바뀔 수 있다(미결 사항 Q8). 선택지를 늘리거나 이름을 바꾸기 쉬운 형태로 다루는 것을 권장하지만 방식은 개발자 판단이다.

**사용자(User)**

| 항목 | 내용 |
|---|---|
| 사용자 식별자 | 시스템 생성 |
| 로그인 수단 | 미정(미결 사항 Q4). MVP 백엔드는 "인증된 사용자를 식별할 수 있다"는 전제만 만족하면 된다 |
| 시간대 | 선택. "오늘"의 기준을 서버가 계산해야 할 때 쓴다. 클라이언트가 현지 날짜를 직접 보내는 방식을 택하면 필요 없을 수 있다(개발자 판단) |
| 가입 시각 | 시스템 생성. G2 측정에 쓴다 |

### 6.3 기능별 상세

#### FR-1 사용자 식별과 데이터 분리 (Must)
- 주요 동작: 모든 기록 관련 요청은 인증된 사용자로만 처리한다. 사용자는 자기 기록만 만들고, 보고, 고치고, 지울 수 있다.
- 인증 방식(이메일·비밀번호, 소셜 로그인, 익명 계정 등)은 미정이다. 개발자는 이후 교체할 수 있는 구조로 최소 구현을 고른다 `[가정]`.
- 수용 기준:
  - [ ] 인증 정보 없이 기록 생성·조회·수정·삭제를 요청하면 거부되고 데이터는 바뀌지 않는다.
  - [ ] 사용자 A가 사용자 B의 기록 식별자로 조회·수정·삭제를 요청하면 거부되고, 응답만으로 그 기록이 존재하는지 알 수 없다(존재하지 않는 기록과 같은 응답).
  - [ ] 목록·요약 조회 결과에 다른 사용자의 기록이 섞이지 않는다.

#### FR-2 식사 기록 생성 (Must)
- 주요 동작: "먹은 것" 텍스트 하나만으로 기록을 저장한다. 나머지 항목은 모두 선택이다. 지난 날짜로도 저장할 수 있다.
- 수용 기준:
  - [ ] "먹은 것"만 보내면 기록이 저장되고, 식사 날짜는 사용자의 오늘로, 끼니 구분·식사량·메모는 비어 있는 상태로 저장된다.
  - [ ] 저장 성공 응답에 생성된 기록의 전체 내용(식별자, 실제 저장된 날짜 포함)이 들어 있다.
  - [ ] "먹은 것"이 없거나, 공백만 있거나, 200자를 넘으면 거부되고, 어떤 항목이 왜 잘못됐는지 알 수 있는 오류를 돌려준다.
  - [ ] 끼니 구분이나 식사량에 정해진 선택지 밖의 값을 보내면 거부된다.
  - [ ] 식사 날짜에 오늘보다 미래 날짜를 보내면 거부된다. 어제, 지난주 등 과거 날짜는 저장된다.
  - [ ] 같은 날, 같은 끼니에 기록을 여러 건 저장할 수 있다(중복으로 거부하지 않는다).
  - [ ] 칼로리·중량 등 정의되지 않은 항목을 함께 보내도 저장되지 않는다(무시하거나 거부하는 방식은 개발자 판단, 일관되게 처리).
  - [ ] 네트워크 재시도로 같은 생성 요청이 두 번 도착해도 기록이 두 건 생기지 않게 할 수 있는 수단이 있다 `[가정]`. 방식은 개발자 판단이며, MVP에서 미루면 남은 일로 보고한다.

#### FR-3 식사 기록 수정 (Must)
- 주요 동작: 자기 기록의 먹은 것, 식사 날짜, 끼니 구분, 식사량, 메모를 고친다. 선택 항목은 비울 수도 있다.
- 수용 기준:
  - [ ] 일부 항목만 고쳐도 나머지 항목은 그대로 유지된다.
  - [ ] 선택 항목(끼니 구분, 식사량, 메모)을 비어 있는 상태로 되돌릴 수 있다.
  - [ ] 수정에도 FR-2와 같은 입력 검증(필수 항목, 길이, 선택지, 미래 날짜 금지)이 적용된다.
  - [ ] 수정 후 수정 시각이 갱신되고, 생성 시각은 바뀌지 않는다.
  - [ ] 존재하지 않거나 남의 기록을 고치려 하면 거부된다(FR-1과 같은 응답).

#### FR-4 식사 기록 삭제 (Must)
- 주요 동작: 자기 기록 한 건을 지운다.
- 수용 기준:
  - [ ] 삭제한 기록은 이후 단건 조회, 날짜별·기간별 조회, 최근 메뉴, 주간 요약 어디에도 나오지 않는다.
  - [ ] 이미 지운 기록을 다시 지우는 요청이 서버 오류(5xx)를 일으키지 않는다.
  - [ ] 남의 기록을 지우려 하면 거부되고 그 기록은 남아 있다.
  - 실행 취소(복구) 기능은 MVP에 없다. 영구 삭제와 일시 보관(soft delete) 중 무엇을 쓸지는 개발자 판단이지만, 어느 쪽이든 사용자에게는 지워진 것으로 보여야 한다.

#### FR-5 날짜별·기간별 기록 조회 (Must)
- 주요 동작: 특정 날짜 하루, 또는 시작일~종료일 기간의 기록을 조회한다. 단건 조회도 제공한다.
- 수용 기준:
  - [ ] 특정 날짜를 지정하면 그 날짜(식사 날짜 기준)의 기록만 돌려준다. 기록이 없는 날은 오류가 아니라 빈 결과다.
  - [ ] 기간을 지정하면 시작일과 종료일을 포함한 기간의 기록을 돌려준다.
  - [ ] 정렬 순서가 정해져 있다: 식사 날짜 → 끼니 구분(아침, 점심, 저녁, 간식, 구분 없음) → 생성 시각 순 `[가정]`.
  - [ ] 한 번에 조회할 수 있는 기간에 상한이 있다(예: 최대 31일 `[가정]`). 상한을 넘거나 시작일이 종료일보다 늦으면 거부된다.
  - [ ] 한 번에 돌려주는 기록 수가 많을 때를 대비한 페이지 나누기 또는 상한이 있다(방식은 개발자 판단).
  - [ ] 단건 조회는 기록의 전체 항목을 돌려준다.

#### FR-6 계정과 전체 데이터 삭제 (Must)
- 주요 동작: 사용자가 탈퇴하면 그 사용자의 계정과 모든 식사 기록을 지운다.
- 이유: 식단 정보는 건강과 관련된 개인정보로 다뤄질 수 있어(미결 사항 Q6), 사용자가 스스로 모두 지울 수 있어야 신뢰를 얻는다.
- 수용 기준:
  - [ ] 탈퇴 후 그 계정의 인증 정보로는 어떤 요청도 처리되지 않는다.
  - [ ] 탈퇴한 사용자의 식사 기록이 조회·집계 어디에도 남지 않는다.
  - [ ] 계정 삭제와 기록 삭제는 함께 성공하거나 함께 실패한다(일부만 지워진 상태로 남지 않는다).
  - 법적 보관 의무 등으로 일정 기간 보관이 필요한지는 미결 사항 Q6에서 확인한다. 확인 전까지는 즉시 삭제를 기본으로 한다 `[가정]`.

#### FR-7 최근 메뉴 목록 조회 (Should)
- 주요 동작: 사용자가 최근에 적은 "먹은 것" 텍스트를 중복 없이 돌려준다. 클라이언트는 이 목록에서 하나를 골라 FR-2로 새 기록을 만든다(별도의 "다시 기록" 동작은 필요 없다).
- 수용 기준:
  - [ ] 최근 30일 `[가정]` 안의 기록에서 "먹은 것" 텍스트를 최대 10개 `[가정]` 돌려준다.
  - [ ] 같은 텍스트(앞뒤 공백 제거 후 완전히 같은 경우)는 한 번만 나온다.
  - [ ] 가장 최근에 쓴 텍스트가 먼저 나온다.
  - [ ] 삭제한 기록의 텍스트는, 같은 텍스트의 다른 기록이 남아 있지 않으면 나오지 않는다.
  - [ ] 기록이 없으면 빈 목록을 돌려준다.

#### FR-8 주간 기록 요약 (Should)
- 주요 동작: 지정한 7일 기간에 대해 "기록한 날 수"와 날짜별 기록 건수, 식사량 선택 분포를 돌려준다. 점수, 목표 달성률, "기록하지 않은 날" 같은 부정적 표현에 쓰일 값은 만들지 않는다(제품 원칙 4).
- 수용 기준:
  - [ ] 기간의 시작일을 지정하면 시작일부터 7일간을 집계한다. 주의 시작 요일은 클라이언트가 정한다.
  - [ ] 결과에 기간 중 기록이 1건 이상 있는 날의 수(0~7)가 들어 있다.
  - [ ] 결과에 날짜별 기록 건수가 들어 있다. 기록이 없는 날은 0건으로 나온다.
  - [ ] 결과에 식사량별(`적게`, `보통`, `많이`, 선택 안 함) 기록 건수가 들어 있다.
  - [ ] 수치는 FR-5로 같은 기간을 조회한 결과와 일치한다.

## 7. 비기능 요구사항

수치는 모두 트래픽 규모 정보가 없어 정한 `[가정]` 값이다.

| 구분 | 요구사항 | 기준 |
|---|---|---|
| 성능 | 기록 생성·수정·삭제·단건 조회 응답 시간 | 정상 부하에서 p95[^1] 500ms 이하 `[가정]` |
| 성능 | 기간 조회(최대 31일), 주간 요약 응답 시간 | 정상 부하에서 p95 1초 이하 `[가정]` |
| 보안 | 전송 구간 암호화 | 모든 요청은 암호화된 연결(HTTPS)로만 받는다 |
| 보안 | 접근 통제 | FR-1 수용 기준을 모든 기록 관련 기능에 적용한다 |
| 개인정보 | 로그 | 로그에 "먹은 것", 메모 내용, 인증 비밀값을 남기지 않는다 |
| 개인정보 | 최소 수집 | MVP에서는 6.2절에 적힌 항목 외 개인정보(실명, 체중, 키, 연락처 등)를 수집하지 않는다. 로그인 수단에 필요한 최소 정보는 예외 |
| 데이터 무결성 | 사용자 날짜 기준 | 식사 날짜는 서버 시간대가 아니라 사용자의 현지 날짜로 저장·조회된다. 예: 한국 시간 00:30에 "오늘"로 저장한 기록이 전날로 저장되지 않는다 |
| 오류 응답 | 일관성 | 입력 오류, 인증 오류, 권한 오류, 없는 리소스가 구분되는 일관된 형식으로 응답하고, 내부 예외 메시지를 노출하지 않는다 |
| 확장성 | 클라이언트 독립 | 플랫폼(iOS, Android, 웹)이 정해지지 않았으므로 특정 클라이언트에 묶이지 않는 API로 만든다 |
| 테스트 | 수용 기준 검증 | FR-1~FR-6의 수용 기준을 자동 테스트로 확인할 수 있다 |
| 접근성 | 해당 없음 | M1은 백엔드만 다룬다. 클라이언트 단계(M2)에서 정한다 |

## 8. 범위 밖

| 항목 | 이유 |
|---|---|
| 사진 인식으로 음식·칼로리 자동 입력 (외부 AI 연동) | 아래 "사진 인식 판단" 참고 |
| 사진 첨부(인식 없이 사진만 저장) | 한 줄 기록만으로 핵심 문제를 검증할 수 있다. 파일 저장·용량·삭제 처리 때문에 MVP 백엔드가 커진다. M4 후보 |
| 칼로리·영양소 입력과 음식 데이터베이스 | 제품의 핵심 가치(숫자 부담 없애기)와 정면으로 충돌한다 |
| 체중 기록 | 숫자 압박을 다시 만들 수 있고, 식단 기록 지속(G2)을 검증하는 데 필요하지 않다. 수요가 확인되면 선택 기능으로 검토 |
| 기록 알림(푸시) | 알림은 "수시로 기록해야 한다"는 강박(P2)을 키울 수 있다. 꺼져 있는 것이 기본인 선택형 부드러운 알림을 M4 후보로 둔다 |
| 연속 기록(스트릭), 배지, 점수 | 기록이 끊기면 실패로 느끼게 만들어 P2를 키운다 |
| 목표 설정(목표 체중, 일일 칼로리 등) | 평가와 압박의 기준이 되어 제품 원칙 4와 충돌한다 |
| 소셜 공유, 커뮤니티, 전문가 코칭 | 핵심 문제와 직접 관련이 없고 개인정보 부담이 커진다 |
| 오프라인 기록과 동기화 충돌 처리 | 클라이언트 플랫폼이 정해진 뒤 결정한다(미결 사항 Q3) |
| 기록 내보내기(CSV 등) | 출시에 필수는 아니다. 개인정보 이동권 대응이 필요하면 다시 검토 |
| 결제, 구독 등 수익화 기능 | 수익 모델이 정해지지 않았다(미결 사항 Q5) |

### 사진 인식(외부 AI 연동)을 MVP에 넣을지 판단

| 선택지 | 얻는 것 | 잃는 것 |
|---|---|---|
| A. MVP에 넣는다 | 타이핑보다 빠를 수 있다(G1). 시장에서 눈에 띄는 기능이다 | 인식 결과가 틀리면 사용자가 고쳐야 해 "정확해야 한다"는 부담(P3)이 되살아난다. 대부분의 인식 서비스는 칼로리 추정이 중심이라 제품 원칙 2와 맞지 않는다. 외부 API 비용, 응답 지연, 장애 대응, 사진 저장·개인정보 처리가 MVP 백엔드 범위를 크게 늘린다. 비용 구조는 수익 모델(Q5)이 없는 상태에서 정하기 어렵다 |
| B. MVP에서 빼고 한 줄 텍스트 + 최근 메뉴로 시작한다 (**추천**) | MVP가 작아 빨리 출시하고 핵심 가설("숫자 없이 기록하면 계속한다")을 깨끗하게 검증할 수 있다. 외부 의존과 비용이 없다 | 사진 한 장으로 끝내는 편리함을 첫 버전에서 주지 못한다. 경쟁 제품보다 기능이 적어 보일 수 있다 |

추천: **B**. 사진 인식이 핵심 문제를 푸는지는 아직 근거가 없고, 오히려 정확도 부담을 다시 만들 위험이 있다. M3 베타에서 G1(기록 시간)이 목표에 못 미치거나 사용자가 사진 기록을 요청하면, 먼저 "인식 없는 사진 첨부"(M4)를 붙이고, 그다음 "칼로리가 아니라 메뉴 이름만 제안하는" 인식 기능을 검토한다.

M1의 기간 근거: 엔터티가 사용자와 식사 기록 두 종류이고 외부 연동이 없다. 인증 방식이 늦게 정해지면 인증 교체 작업이 추가로 생길 수 있다.

### M2 웹 1차 구현 메모 (2026-10-26)

- 구현: `web/`. 가입 없이 시작(동의 필수) → 기록·수정·삭제·지난 날짜 기록 → 최근 메뉴 → 한 주 보기 → 계정 연결·로그아웃·탈퇴. US-1~US-8을 브라우저 자동 테스트(`web/tests/e2e.mjs`)로 끝까지 확인했다.
- 백엔드 추가: 가입 없이 시작, 계정 연결, 쓰는 동안 연장되는 세션, 동의 시각 저장(마이그레이션 0002).
- **G1 측정 이벤트는 M3 준비로 미뤘다.** 이유: 사용 행동 로그 수집은 동의 항목과 보관 기준(Q6)에 들어가야 하고, 베타 참가자에게만 받아도 측정 목적을 이룰 수 있다. 대가: 베타 시작 전에 이벤트 수집과 별도 동의를 먼저 만들어야 한다.
- 동의 문구는 법률 검토 전 초안이다.

## 11. 미결 사항

2026-10-26 사용자 결정: 기한 미정, 대상은 현대인 전체, 웹 먼저 출시 후 모바일 앱으로 확장. 나머지는 제품 목적(기록 부담 최소화)에 따라 판단하도록 위임받아 아래처럼 정했다.

- [x] Q1. 출시 기한 → 정하지 않는다. 마일스톤 기간은 순서와 규모를 가늠하는 추정치로만 쓴다.
- [x] Q2. 대상 사용자 → 현대인 전체. 우선순위는 유형 A(기록 포기 경험자) → B → C.
- [x] Q3. 플랫폼 → 웹 먼저, 이후 모바일 앱. API는 웹과 앱이 함께 쓰도록 헤더 토큰 인증과 CORS 설정을 둔다. 오프라인 기록은 웹 단계에서 하지 않고 앱 단계에서 다시 판단한다.
  - 장점: 설치 없이 바로 써 볼 수 있어 첫 기록까지의 장벽이 낮고, 한 번에 여러 기기에서 검증할 수 있다.
  - 단점: 앱 대비 알림·홈 화면 접근성이 약하다. 다만 이 제품은 알림 압박을 피하는 방향이라 영향이 작다.
- [x] Q4. 로그인 수단 → M1은 이메일·비밀번호 최소 구현을 유지하고, M2 웹에서 "가입 없이 바로 기록 시작 → 원할 때 계정 연결"을 추가한다. 소셜 로그인은 앱 단계에서 검토한다.
  - 이유: 가입 절차 자체가 첫 기록을 막는 부담이다.
  - 대가: 익명 사용자는 기기를 바꾸면 기록을 잃을 수 있어, 계정 연결을 부담 없이 안내하는 화면이 필요하다.
- [x] Q5. 수익 모델 → 베타(M3)까지 무료. 외부 유료 API가 필요한 기능은 넣지 않는다. 수익화는 베타 결과를 보고 정한다.
- [~] Q6. 민감정보 여부 → 법적 판단은 내릴 수 없으므로, 확인 전까지 건강 관련 민감정보로 간주해 보수적으로 설계한다(최소 수집, 전송 구간 암호화, 탈퇴 시 즉시 삭제, 로그에 기록 내용 미저장, M2에서 수집 동의 화면). **출시 전 법률·개인정보 전문가 확인은 여전히 필요하다.**
- [x] Q7. 사전 검증 → 별도 인터뷰 없이 베타 테스트(M3)의 지표 G1~G4로 검증한다.
- [x] Q8. 끼니·식사량 선택지 → 현재 선택지와 "구분 없음"을 유지하고, 베타에서 "구분 없음" 사용 빈도와 사용자 의견을 보고 조정한다.
- [x] Q9. 기술 스택 → 제약 없음. 백엔드 개발자 판단에 맡긴다.
- [x] Q10. 팀 규모 → 정보 없음. 기간 추정은 역할별 1명 기준을 유지한다.
