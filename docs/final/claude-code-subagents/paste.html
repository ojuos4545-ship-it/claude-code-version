이 글을 끝까지 따라오시면 기본 서브에이전트에게 조사를 맡기는 법, 나만의 서브에이전트를 만드는 법, 원하는 일꾼을 확실히 부르는 법까지 손에 익히실 수 있습니다.


지난 글 '클로드 코드 스킬 사용법'에서 "스킬은 지금 대화에 불러오는 설명서, 서브에이전트는 따로 일한 뒤 요약만 돌려주는 일꾼"이라고 구분해 드렸죠.

오늘은 바로 그 일꾼 이야기입니다. 첫 글 '클로드 코드 핵심 기능 5가지'에서 넷째로 소개한 기능을 손으로 익혀 보는 실습편이기도 해요.

앞 글을 못 보셨더라도 이 글만 읽고 바로 시작하실 수 있게 썼습니다.

말 쉬운 뜻
서브에이전트(subagent) 메인 대화와 따로 일하고, 끝나면 보고만 돌려주는 보조 AI

프론트매터 파일 맨 위 ---와 --- 사이에 항목: 값 모양으로 적는 설정


이 글의 기능 설명은 조사일(2026-10-28)에 열어 본 공식 문서를 바탕으로 썼습니다. 그날 공식 변경 이력의 최신 버전은 v2.1.312였어요.

서브에이전트는 최근에도 동작이 여러 번 바뀐 기능이라, claude --version으로 내 버전을 먼저 확인하고 글 아래 공식 문서도 함께 봐 주세요.


중간중간 나오는 '직접 해 본 결과'는 같은 날 Claude Code 2.1.312 버전과 claude-opus-5-5 모델로 돌린 기록입니다.

이번 연습 프로젝트는 앞 글들의 할 일 목록이 아니에요. 제 저장소에 있는 식단 기록 앱의 백엔드(파이썬 파일 30개, 약 172KB)를 복사해 git 폴더로 만들어 썼습니다.


왜 바꿨을까요? 할 일 목록은 파일이 4개뿐이라 '읽을 거리가 많은 조사'를 맡겨 보기에는 너무 작았거든요.

실험마다 새로 복사해서 앞 실험의 흔적이 남지 않게 했습니다.


질문 하나를 보내고 답을 받는 방식(claude -p)이라, 서브에이전트에 맡겼는지는 실행 기록에 남는 위임 흔적(Agent 도구 호출)으로 판정했어요.

개인 설정이 섞이지 않게 빈 홈 폴더로 실행했고, 직접 만든 서브에이전트는 모두 프로젝트의 .claude/agents/에 두었습니다.

맡길지 말지는 Claude가 그때그때 정하는 일이고 경우마다 1~3번씩 돌린 결과라, 여러분 화면에서는 다르게 나올 수 있어요.



1. 서브에이전트가 뭐예요? - 스킬이나 CLAUDE.md와 무엇이 다를까요?


공식 문서는 클로드 코드 서브에이전트를 "특정 유형의 작업을 맡는 전문 AI 보조"라고 소개합니다.

각 서브에이전트는 자기 컨텍스트 창에서 자기 지침, 쓸 수 있는 도구, 독립된 권한을 따로 가지고 일해요.

일하는 동안 읽은 파일과 검색 결과는 그 안에 머물고, 메인 대화에는 최종 보고만 돌아옵니다.


공식 문서가 서브에이전트를 권하는 순간은 다시 볼 일 없는 검색 결과나 로그, 파일 내용으로 메인 대화가 넘칠 때예요.

같은 지침의 일꾼을 자꾸 띄우게 된다면, 아예 파일로 정의해 두는 편이 낫다고 하고요.


비슷한 기능들과 나란히 놓으면 차이가 잘 보여요. 공식 기능 비교 문서의 내용을 옮겼습니다.


구분 하는 일 언제 쓰나
CLAUDE.md 매 대화 자동으로 읽히는 맥락 프로젝트 규칙, "항상 이렇게 해"
스킬 필요할 때 불러오는 지침·절차 다시 쓰는 절차, 참고 자료
서브에이전트 따로 떨어진 곳에서 일하고 요약만 돌려줌 맥락 분리, 동시 작업, 전문 일꾼
훅 정해진 순간마다 명령 실행 매번 반드시 일어나야 하는 자동화


스킬과 가장 많이 헷갈리실 텐데요. 스킬 내용은 지금 대화에 더해지고, 서브에이전트는 별도의 창에서 따로 돈다는 점이 갈림길입니다.

Anthropic의 Claude 블로그도 중간 결과로 메인 대화를 어지럽히는 곁일은 서브에이전트에게, 단계를 메인에서 지켜보며 조정하고 싶은 절차는 스킬로 나누라고 정리해요.


여기서 꼭 기억하실 점이 하나 있습니다.

일반 서브에이전트는 우리가 나눈 대화를 모릅니다. 메인이 이미 읽은 파일도, 이미 불러온 스킬도 몰라요.


Claude가 써 주는 위임 메시지와 CLAUDE.md, git 상태 정도만 받아 들고 일을 시작합니다. (뒤에서 만날 내장 Explore·Plan은 CLAUDE.md와 git 상태도 읽지 않아요.)


예외도 있습니다. 대화를 통째로 물려받는 포크(fork)라는 방식이 기본으로 켜져 있어서, Claude가 필요하다고 보면 스스로 띄우기도 해요.

포크 이야기는 6절 자주 묻는 질문에서 조금 더 풀어 드릴게요.


【사진 02】 02_card_side-work.png


그렇다면 언제 맡기고, 언제 메인 대화에서 그냥 하는 게 나을까요? 공식 문서의 기준을 추리면 이렇습니다.


• 메인 대화가 나을 때: 주고받기가 잦은 일, 여러 단계가 맥락을 많이 공유하는 일, 빠르고 작은 수정, 기다리는 시간이 중요한 일

• 서브에이전트가 나을 때: 메인에 남길 필요 없는 긴 출력이 나오는 일, 도구나 권한을 좁혀야 하는 일, 혼자 끝내고 요약으로 돌려줄 수 있는 일


이미 대화에 나온 내용을 두고 잠깐 곁가지로 묻고 싶을 때는 서브에이전트 대신 /btw를 쓰라는 안내도 있어요.

/btw는 대화 전체를 보지만 도구가 없고, 서브에이전트는 도구가 있지만 받은 요청에서부터 출발합니다.



2. [1단계] 기본 서브에이전트에 맡겨 보기 - Explore에게 조사를 시키면 뭐가 달라질까요?


서브에이전트를 하나도 만들지 않았어도 바로 일을 넘길 수 있는 일꾼이 이미 있습니다. 클로드 코드에 들어 있는 내장 서브에이전트예요.

처음에는 아래 셋만 알아 두셔도 충분합니다.


이름 하는 일 도구 CLAUDE.md
Explore 파일 찾기, 코드 검색, 프로젝트 둘러보기 읽기 전용(고치기·새로 쓰기 불가) 읽지 않음
Plan 플랜 모드에서 계획 세우기 전 조사 읽기 전용 읽지 않음
general-purpose 찾아보고 고치기까지 함께 필요한 여러 단계 작업 서브에이전트가 쓸 수 있는 모든 도구 읽음


이 밖에도 클로드 코드 사용법 질문에 답하는 claude-code-guide 같은 내장 일꾼이 몇 개 더 있어요.

Explore는 불릴 때 quick, medium, very thorough 중에서 얼마나 꼼꼼히 찾을지 수준을 함께 받습니다.


공식 모범 사례 문서에 따르면 넓은 검색은 Claude가 알아서 Explore에게 보내는 경우가 많아, 대부분은 따로 부탁할 필요가 없어요.

다만 SDK 문서에는 일부 모델에서는 요청이 없으면 서브에이전트를 부르지 말라는 안내가 들어간다는 설명도 있습니다. Explore에게 넘기고 싶다면 요청에 이름을 적어 주는 편이 마음 편해요.


아래 순서대로 차근차근 따라와 주세요.


1. 연습 폴더에서 시작: 파일이 여럿 있는 git 폴더에서 claude를 실행합니다.

2. 이름을 넣어 요청: 질문 앞에 "Explore 서브에이전트에게 맡겨서 조사해 줘."를 붙여 보냅니다.

3. 진행 상황 보기: 맡긴 일은 프롬프트 아래 서브에이전트 패널이나 /tasks에서 확인합니다. (대화 화면에서는 서브에이전트가 기본으로 백그라운드에서 돌아요.)

4. 보고 받기: 일이 끝나면 결과가 대화에 도착하고, Claude가 그 보고를 바탕으로 답합니다.


제가 실험에서 보낸 요청은 "Explore 서브에이전트에게 맡겨서 조사해 줘." 뒤에 로그인 토큰 처리 방식을 묻는 질문을 이어 붙인 문장이었어요.


【사진 03】 03_card_prompt.png


비교를 위해 같은 질문 앞에 "서브에이전트는 쓰지 말고 직접 파일을 읽어서 조사해 줘."를 붙인 버전도 만들어, 두 방식을 각각 두 번씩 보냈습니다.

살펴본 건 메인 대화가 받아 든 분량이에요. Claude가 도구를 써서 돌려받은 결과(파일 내용, 명령 출력, 서브에이전트 보고)의 글자 수를 모두 더했습니다.


회차 방식 메인 대화의 도구 호출 서브에이전트 안의 도구 호출 메인 대화로 돌아온 분량 최종 답

1 Explore에 맡김 1회 (Agent 1) 4회 6,299자 843자
2 직접 2회 (Bash 2) 없음 28,172자 933자
2 Explore에 맡김 1회 (Agent 1) 4회 4,235자 995자

맡겼을 때 메인 대화로 들어온 분량은 같은 회차에 직접 했을 때의 약 1/7~1/3이었어요.

파일을 읽는 일은 서브에이전트 안에서 일어났고, 메인 대화는 Agent 호출 한 번으로 보고만 받았기 때문입니다.


답의 핵심은 두 방식이 같았습니다.

로그인 토큰은 JWT가 아니라 secrets.token_urlsafe(32)로 만든 무작위 문자열이고, 서버 DB의 sessions에 기록해 두었다가 요청마다 대조한다는 결론이었어요.

최종 답 길이도 843~995자로 비슷했고요.


다만 이 숫자는 메인 대화 기준이라는 점을 놓치지 마세요.

서브에이전트가 읽은 분량이 사라진 게 아니라 서브에이전트 쪽으로 옮겨 간 것이고, 이번 실험에서 전체 사용량이나 비용은 재지 않았습니다. 비용 이야기는 5절에서 따로 다룹니다.


그럼 조사는 늘 맡기는 편이 좋을까요? 공식 문서 안에서도 강조점이 조금 다릅니다.


기능 비교 문서는 컨텍스트가 차오를 때 서브에이전트를 쓰라고 권해요. 반면 모범 사례 문서는 컨텍스트 창이 1M 토큰으로 넓어진 지금은 공간이 모자랄 일이 드물다며, '컨텍스트를 아끼려고' 쓰는 건 예전 조언이라고 분류합니다.

대신 동시에 여러 일을 돌릴 때, 긴 출력을 메인 밖에 둘 때, 코드를 쓴 과정을 보지 않은 눈으로 검토받을 때, 도구를 좁혀 줄 때는 여전히 쓸모가 있다고 해요.


📌 전문가 Tip: "vendor 폴더는 보지 마"처럼 CLAUDE.md에만 적어 둔 규칙은 Explore가 모릅니다. 조사를 맡길 때 꼭 지켜야 할 조건은 요청 문장에 한 번 더 적어 주세요. 공식 문서도 같은 방법을 권합니다.



3. [2단계] 내 서브에이전트 만들기 - 파일 한 장에 무엇을 적을까요?


기본 일꾼에 익숙해졌다면 이제 내 일에 맞는 일꾼을 들일 차례입니다.

클로드 코드 서브에이전트는 마크다운 파일 한 장이면 만들어져요. 두는 곳에 따라 쓸 수 있는 범위가 달라집니다.


• .claude/agents/: 이 프로젝트에서만 사용. 커밋하면 팀원과 함께 씀

• ~/.claude/agents/: 내 컴퓨터의 모든 프로젝트에서 사용 (~는 내 홈 폴더)


같은 이름이 두 곳에 있으면 프로젝트 쪽이 이깁니다.

(회사 관리 설정이나 실행 옵션 --agents로 넣은 것은 그보다 앞서고, 플러그인에 든 것은 가장 뒤예요.)


3-1. /agents는 이제 만들기 화면이 아니에요


예전 글이나 영상에서 "/agents를 입력하면 만들기 화면이 열린다"는 설명을 보셨을 수도 있어요.

그건 v2.1.197 이하의 이야기입니다. 지금 /agents를 입력하면 Claude에게 부탁하거나 .claude/agents/, ~/.claude/agents/의 파일을 직접 고치라는 안내만 나와요.


그래서 지금 만드는 방법은 두 가지입니다.


1. Claude에게 부탁하기: 원하는 일꾼과 저장 위치를 말로 설명합니다. 공식 퀵스타트의 예시를 우리말로 줄여 옮기면 "~/.claude/agents/에 개인용 code-improver 서브에이전트를 만들어 줘. 읽기 전용으로, Sonnet을 쓰게 해 줘." 같은 식이에요. (만들어지면 파일을 열어 tools 줄이 요청과 맞는지 꼭 확인하세요.)

2. 파일 직접 쓰기: 아래 형식대로 저장합니다.


처음이라면 첫째 방법이 가장 쉽고, 공식 문서도 이쪽을 먼저 안내해요.

다만 파일 모양을 알아야 Claude가 만든 결과도 확인할 수 있으니, 이 글에서는 직접 써 보겠습니다.


3-2. 파일 모양 - 프론트매터와 본문


서브에이전트 파일은 두 부분으로 나뉩니다.

맨 위 --- 사이의 프론트매터에는 이름과 언제 맡길지, 쓸 도구를, 그 아래 본문에는 서브에이전트가 따를 지침을 적어요.


본문은 곧 그 서브에이전트의 시스템 프롬프트(일을 시작하기 전에 받는 기본 지침)가 됩니다.

서브에이전트는 클로드 코드의 기본 지침 대신 이 본문과 작업 폴더 같은 환경 정보만 받으니, 할 일을 또렷하게 적어 두는 게 좋아요.


항목 필수 하는 일 안 적으면
name 예 서브에이전트 이름표. 공식 예시는 영어 소문자와 하이픈 서브에이전트가 아니라 옆에 둔 참고 문서로 취급
description 예 무엇을 하고 언제 맡길지. Claude가 보고 고름 파일을 건너뜀(이유는 디버그 기록에만 남음)
tools 아니요 쓸 수 있는 도구 목록 쓸 수 있는 도구를 모두 물려받음
model 아니요 haiku, sonnet, opus, inherit(메인과 같게) 등 대개 메인 대화와 같은 모델


이 밖에도 permissionMode, skills, color 같은 선택 항목이 여럿 있지만, 처음에는 위 넷이면 넉넉합니다.

항목 이름은 대소문자까지 정확히 적어야 해요. 모르는 이름은 오류 없이 무시되거든요.


3-3. 따라 하기 - 읽기 전용 리뷰어 만들기


제가 실험에 쓴 리뷰어를 그대로 만들어 보겠습니다.


1. 폴더 만들기: 프로젝트 안에 .claude/agents/ 폴더를 만듭니다. (클로드 코드를 켠 뒤에 이 폴더를 처음 만들었다면, 한 번 다시 시작해야 인식돼요.)

2. 파일 저장: 그 폴더에 reviewer.md라는 이름으로 아래 내용을 저장합니다.

3. 목록 확인: 입력창에 @를 입력해 자동 완성 목록에 reviewer가 보이는지 봅니다.

4. 맡겨 보기: "reviewer 서브에이전트에게 맡겨서 (파일 이름) 코드를 검토해 줘"처럼 이름을 넣어 부탁합니다.


---

name: reviewer

description: 코드를 읽고 버그·보안 문제를 찾아 근거와 함께 보고하는 읽기 전용 리뷰어. 사용자가 코드 리뷰, 검토, 점검, 버그 찾기를 요청하면 사용한다.

tools: Read, Grep, Glob

---


당신은 코드 리뷰어다. 코드를 읽고 버그, 보안 문제, 읽기 어려운 부분을 찾아 근거(파일:줄)와 함께 보고한다.

보고 첫 줄에 반드시 `[reviewer 에이전트 보고]`라고 쓴다.

파일을 고치지 않는다. 고칠 방법은 제안으로만 적는다.


본문 둘째 줄의 [reviewer 에이전트 보고]는 실험용 표시예요. 보고가 이 서브에이전트에게서 왔는지 눈으로 가려내려고 넣었습니다.

파일 이름과 name을 같게 맞춘 것도 헷갈리지 않으려는 습관일 뿐, 클로드 코드는 name으로만 서브에이전트를 구별해요.


이미 있던 폴더에 파일을 더하거나 고치면 몇 초 안에 반영되고, 다음에 맡길 때부터 새 내용이 쓰입니다.

3-4. tools 한 줄이 '읽기 전용'을 만듭니다


이 파일에서 가장 중요한 줄은 tools: Read, Grep, Glob입니다.

이 줄이 있으면 reviewer는 읽기(Read), 내용 검색(Grep), 파일 찾기(Glob) 세 도구만 쓸 수 있어요.

tools 줄을 아예 빼면 메인 대화에서 쓸 수 있는 도구를 모두 물려받습니다. (질문 창 띄우기처럼 서브에이전트에서는 원래 빠지는 몇 가지는 제외예요.)


첫 글 '클로드 코드 핵심 기능 5가지'에서는 서브에이전트를 "제한된 도구를 가지고" 일하는 보조 AI라고 소개했는데요.

정확히 말하면 tools로 정해 줄 때만 제한되고, 생략하면 거의 모든 도구를 씁니다. 여기서 보완해 둘게요.

그 글에서 말씀드린 제 조사 담당 서브에이전트가 웹 검색과 읽기·쓰기만 하는 것도, 파일에 tools: WebSearch, WebFetch, Read, Glob, Grep, Write를 적어 두었기 때문이에요.


정말 도구 목록이 막아 줄까요? 직접 확인해 봤습니다.

reviewer에게 보낸 요청은 "reviewer 서브에이전트에게 맡겨서 app/config.py 맨 위에 '# 검토 완료' 주석 한 줄을 추가하게 해 줘. 너는 직접 파일을 고치지 말고, 서브에이전트가 한 결과만 그대로 전해 줘."였어요.


기본 권한 모드에서는 reviewer가 불렸지만 파일은 그대로였습니다.

돌아온 답은 "reviewer가 쓸 수 있는 도구는 Read, Grep, Glob뿐이라 파일을 고칠 수 없습니다"였고, 파일을 고치지 않는다는 역할 지침도 이유로 들었어요.


막은 것이 도구 목록인지 지침인지 확인하려고 조건을 바꿔 두 번 더 돌렸습니다.

본문의 "파일을 고치지 않는다…"를 "요청받으면 파일도 직접 고친다."로 바꾸고, 파일 수정을 자동 승인하는 acceptEdits 모드로 실행했어요.


경우 지침 tools 줄 결과
기본 권한 모드 고치지 않는다 Read, Grep, Glob 못 고침. 도구와 지침을 이유로 듦
acceptEdits 요청받으면 고친다 Read, Grep, Glob 못 고침. "쓸 수 있는 도구는 Read, Grep, Glob뿐"
acceptEdits 요청받으면 고친다 없음(생략) 첫 줄에 # 검토 완료 추가됨


지침이 "고쳐라"여도 고치는 도구가 없으니 손을 대지 못했고, tools 줄을 지우자 물려받은 도구로 실제로 고쳤어요.

공식 모범 사례 문서도 이렇게 도구를 좁힌 리뷰어는 프롬프트로 부탁한 것이 아니라 클로드 코드가 강제하는 읽기 전용이라고 설명합니다.

몇 가지 덧붙일게요.


• Bash는 신중하게: Bash를 주면 셸 명령으로도 파일을 바꿀 수 있어요. 완전한 읽기 전용을 원하면 Read, Grep, Glob 세 가지만 주는 편이 안전합니다.

4-1. 알아서 맡기게 하려면 description을 구체적으로


Claude는 요청 내용과 각 서브에이전트의 description, 지금까지의 맥락을 함께 보고 누구에게 넘길지 정합니다.

공식 문서가 꼽는 요령을 추리면 이래요.


• 언제 쓰는지 분명히: "사용자가 코드 리뷰, 검토, 점검을 요청하면"처럼 맡길 상황을 적기

• 하나만 골라지게: 비슷한 서브에이전트끼리 설명이 겹치지 않도록 구체적으로

• 짧게: 자세한 지침은 본문으로. 본문은 실제로 맡길 때만 읽힘

• 적극적으로 쓰게 하려면: "use proactively" 같은 문구 넣기


설명 한 줄로 얼마나 달라질까요? 본문과 tools는 그대로 두고 description만 바꾼 reviewer 세 가지로 견주어 봤어요.

요청은 이름을 넣지 않은 "app/api/ratelimit.py 코드 리뷰해 줘. 버그가 있으면 알려 줘."였고, 경우마다 세 번씩 보냈습니다.

4-2. 원하는 일꾼을 지정하려면 @멘션


자동 위임은 결국 Claude의 판단이라 매번 같지 않습니다.

특정 서브에이전트를 반드시 돌리고 싶다면 입력창에 @를 치고 자동 완성 목록에서 고르세요. 직접 쓴다면 모양은 이렇습니다.


@"reviewer (agent)" app/api/ratelimit.py 코드 리뷰해 줘. 버그가 있으면 알려 줘.


@agent-reviewer처럼 이름 앞에 agent-를 붙여 적어도 됩니다.


이번에는 0/3이었던 모호한 설명("도움을 준다.")의 reviewer를 그대로 두고, 위 문장을 두 번 보냈습니다.

두 번 모두 reviewer가 불렸고, 서브에이전트 안에서 도구를 각각 11번 써 가며 파일을 살폈어요.

메인 Claude는 보고를 받은 뒤 주요 지적을 파일과 직접 대조해 확인했다고 답했습니다.


질문 한 번 보내는 claude -p 방식에서 멘션이 어떻게 처리되는지는 공식 문서에 따로 적혀 있지 않아요.

멘션 기능 덕분인지 Claude가 문장 속 이름을 보고 넘긴 것인지는 기록만으로는 구분이 안 되지만, 두 번 모두 맡겼다는 결과는 같았습니다.


이름을 말로 부르는 방법은 어땠을까요? 2단계 실험에서 "reviewer 서브에이전트에게 맡겨서 …"로 시작한 요청은 세 번 모두 reviewer에게 갔어요.

그래도 공식 서브에이전트 문서는 이름을 말로 부르면 "대개" 맡기고, @멘션은 실행을 "보장"한다고 구분합니다.

SDK 문서에는 이름만 언급해도 그 에이전트를 직접 부른다는 설명이 있지만, 이 글은 클로드 코드 문서를 따라 "확실히 하려면 @멘션"으로 정리할게요.


@멘션에 대해 알아 둘 것도 있어요. 멘션은 어느 서브에이전트가 돌지를 정할 뿐, 그 서브에이전트에게 넘길 작업 설명은 여전히 메인 Claude가 씁니다.

그러니 꼭 전해야 할 파일 경로나 오류 메시지, 이미 정한 결정 사항은 요청 문장에 직접 담아 주세요.



5. 안 될 때와 주의할 점 - 비용과 권한은 어떻게 될까요?


"분명 만들었는데 목록에 안 보여요" 싶을 때가 있죠. 만든 클로드 코드 서브에이전트가 보이지 않거나 불리지 않는다면 아래 순서로 살펴보세요.


1. 목록 확인: 입력창에 @를 쳐서 자동 완성에 이름이 뜨는지 봅니다.

2. 첫 줄과 필수 항목: 파일 첫 줄이 ---인지, name과 description이 모두 있는지 확인합니다. (하나라도 빠지면 화면에 알림 없이 서브에이전트로 잡히지 않아요.)

3. 콜론과 공백: 설명 안에 :가 있다면 큰따옴표로 감쌌는지 봅니다.

4. 폴더를 새로 만들었는지: 클로드 코드를 켠 뒤에 agents 폴더를 처음 만들었다면 다시 시작합니다.

5. 문법 검사: claude plugin validate .claude/agents(v2.1.233 이상)로 프론트매터를 검사합니다. 항목 이름 오타는 claude --debug로 실행한 뒤 ~/.claude/debug/<세션 ID>.txt에서 does not recognize or apply를 찾아보세요(v2.1.296 이상).


5-1. 비용 - 맡긴다고 공짜는 아니에요


맡기면 비용이 줄어들까요? 공식 문서의 답은 "그렇지 않다"에 가깝습니다.

서브에이전트도 자기 몫의 요청을 따로 보내고, 그 사용량은 메인 대화와 같은 사용량 한도에서 빠져요.

돌아온 보고도 메인 대화에 들어가니, 자세한 보고를 여럿 받으면 그만큼 자리를 차지합니다.


시간도 공짜가 아니에요. 새 서브에이전트는 메인이 이미 알고 있는 맥락을 처음부터 다시 모아야 해서, 그 자리에서 바로 하는 것보다 느릴 수 있습니다.

공식 모범 사례 문서는 "더 좋은 답을 얻으려고 맡긴다"는 기대도 틀렸다고 짚어요.

기본은 같은 모델(또는 더 작은 모델)이 같은 일을 하는 것이라, 리뷰어가 도움이 되는 이유는 내 추론 과정을 보지 않은 새 눈이기 때문이지 맡긴 것 자체 때문이 아니라는 설명입니다.


장점 단점
긴 검색 결과·로그를 메인 대화 밖에 둠 메인 대화와 같은 사용량 한도에서 빠짐
서로 독립된 일을 동시에 돌림 맥락을 새로 모으느라 느릴 수 있음
코드를 쓴 과정을 안 본 눈으로 리뷰 대화 기록을 모름(포크 제외)
tools로 할 수 있는 일을 강제로 좁힘 맡긴다고 답이 더 똑똑해지지는 않음


【사진 08】 08_table_pros-cons.png


아끼는 방법도 공식 문서에 나와 있어요.


• 단순한 일은 작은 모델로: 어떤 모듈을 불러 쓰는 파일 모으기, 문서 링크 확인 같은 일은 model: haiku가 훨씬 쌉니다.

• 짧게 보고받기: 본문에 "5줄 이내로 요약"처럼 보고 길이를 정해 둡니다.

• 사용량 확인: /usage에서 서브에이전트별 사용 비중을 볼 수 있어요. (Pro·Max·Team·Enterprise 요금제)


5-2. 권한과 중첩 - 혼자 권한을 높이지는 못해요


두 편 전 글 '클로드 코드 권한 모드 사용법'에서 다룬 모드와는 이렇게 이어집니다.

서브에이전트는 대부분 메인 대화의 권한 모드를 따라요. 메인이 auto나 acceptEdits라면 서브에이전트도 같은 모드로 돌고, 메인이 플랜 모드라면 서브에이전트도 플랜 모드에 머뭅니다.


메인이 기본 모드일 때 파일에 permissionMode: bypassPermissions를 적어 두어도 메인 모드가 그대로 유지되기 때문에(v2.1.267 이상), 서브에이전트가 혼자 권한을 높일 수는 없어요.

백그라운드에서 도는 서브에이전트가 허락을 구하면, 메인 화면에 어느 서브에이전트가 묻는지 함께 표시됩니다.


서브에이전트가 또 다른 서브에이전트를 부르는 중첩도 기본으로 됩니다. 공식 문서 기준으로 메인 아래 3계층까지예요.

맨 아래 계층에 닿은 서브에이전트는 더 맡기지 못하고 받은 일을 직접 처리합니다.


5-3. 보안 - 남이 만든 일꾼은 읽어 보고 쓰기


에이전트 파일의 본문은 그 자체가 지시문입니다. 게다가 tools가 비어 있으면 쓸 수 있는 도구를 모두 쥐고 일하죠.

인터넷이나 남의 저장소에서 받은 서브에이전트는 꼭 열어서 읽어 본 뒤에 쓰세요.


저장소에 든 서브에이전트 파일에 적힌 훅과, 파일 안에 직접 정의한 MCP 서버는 그 폴더를 믿는다고 확인하기 전에는 작동하지 않습니다.

다만 서브에이전트 자체는 그 전에도 돌아간다는 점을 기억해 두세요.


📌 전문가 Tip: 남의 저장소에서 claude -p를 돌려야 한다면 --bare 옵션을 알아 두세요. 프로젝트에 든 서브에이전트, 훅, 스킬, 플러그인 등을 읽지 않고 실행합니다. 대신 프로젝트 쪽 설정을 하나도 쓰지 않는 실행이라, 필요한 경우에만 고르시면 됩니다.



6. 자주 묻는 질문 - 처음 쓰면 무엇이 헷갈릴까요?


Q. 만든 서브에이전트 목록은 어디서 보나요?

입력창에 @를 치면 나오는 자동 완성 목록에서 확인합니다. 지금 돌고 있거나 끝난 서브에이전트는 /tasks와 프롬프트 아래 서브에이전트 패널에서 보여요.

터미널의 claude agents 명령은 이름과 달리 서브에이전트 목록이 아니라, 백그라운드 세션을 보는 화면을 엽니다.


Q. 맡겨 놓고 기다리지 않은 채 다음으로 넘어가요.

조사일 기준 대화 화면에서는 서브에이전트가 기본으로 백그라운드에서 돌고, 끝나면 결과가 도착합니다. 포크 모드가 켜져 있는 동안은 Claude가 서브에이전트를 기다릴 수 없어요.

꼭 기다리게 하고 싶다면 CLAUDE_CODE_FORK_SUBAGENT=0으로 포크 모드를 끄고 다시 시작한 뒤, "리뷰어를 돌리고 보고를 기다려"처럼 요청하라고 공식 문서는 안내합니다.


Q. 포크는 일반 서브에이전트와 뭐가 다른가요?

포크는 지금까지의 대화 전체를 물려받은 서브에이전트예요. 설명을 다시 하지 않아도 되고, 메인 대화와 저장해 둔 처리 결과(프롬프트 캐시)를 나눠 써서 같은 맥락이 필요한 일에는 새 서브에이전트보다 쌉니다.

대신 대화를 모르는 데서 오는 깨끗한 시선은 없어요. 직접 띄우려면 /subtask <작업>을 씁니다.


Q. 스킬과 서브에이전트, 뭘 먼저 만들까요?

단계를 메인 대화에서 보면서 조정하고 싶은 절차라면 스킬, 중간 결과는 볼 필요 없고 결론만 받으면 되는 곁일이라면 서브에이전트가 맞아요.

둘을 합칠 수도 있습니다. 서브에이전트 파일의 skills: 항목에 스킬 이름을 적으면 시작할 때 그 스킬 본문을 미리 싣고 일하고, 반대로 스킬에 context: fork를 적으면 그 스킬이 서브에이전트 안에서 따로 돌아요.

단 지난 글의 blog-titles처럼 disable-model-invocation: true인 스킬은 미리 실을 수 없습니다.


Q. 여러 서브에이전트를 한꺼번에 돌릴 수 있나요?

네. 조사일 기준 동시에 기본 20개까지 돌 수 있어요(v2.1.217 이상). "인증, 데이터베이스, API 모듈을 각각 다른 서브에이전트로 동시에 조사해 줘"처럼 부탁하면 됩니다.

다만 각자 자세한 결과를 돌려주면 그만큼 메인 대화 자리를 차지한다는 점을 공식 문서도 경고해요.
